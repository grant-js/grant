# 0010 — CDM imports carry bcrypt password hashes into the credential store, and project apps can sign in with them

- **Status**: Proposed
- **Amended by**: [0011](./0011-password-as-a-scoped-credential.md) (Proposed). Passwords stop living in the
  global email authentication method: they become a credential with a scope, `platform` or one
  `project`, and an imported password is a project credential that only that project's apps
  verify. Rules 3 to 6 and 8 of (a), Security notes 1 and all of (b) below
  describe what v1.16.0 shipped; where 0011 is accepted it governs. This record is left as written.
- **Date**: 2026-10-15
- **Context**: an adopter migrating users from a legacy system, who wants them to sign in to
  project apps with their existing password instead of being moved onto magic link
- **Depends on**: [0008](./0008-per-project-oauth-connections.md) (project-app sign-in),
  [0009](./0009-cdm-import-by-reference.md) (where a CDM document is kept while a job runs)
- **Scope**: two parts, decided together and landed separately. **(a)** CDM import of
  pre-hashed bcrypt credentials: implemented with this record. **(b)** email and password as a
  per-project-app sign-in option, verified against the same stored hash: described here, built in
  a follow-up slice.

## Context

**What the legacy system holds.** The adopter's system hashes passwords with Go's
`golang.org/x/crypto/bcrypt`: `GenerateFromPassword` at `DefaultCost` (10), producing `$2a$`
hashes, verified with `CompareHashAndPassword`.

**What Grant already stores and verifies.** A platform email and password credential is a bcrypt
hash at `providerData.hashedPassword` of the user's email authentication method. It is written
by registration (`user-authentication-methods.service.ts:391-396`), by password reset (`:705-708`)
and by change or first set (`:833`), and read by platform login: `auth.handler.ts:422-428` takes
`providerData.hashedPassword` and calls `verifySecret`, which is node `bcrypt.compareSync`
(`token.lib.ts:46-47`). `compareSync` accepts `$2a$`, `$2b$` and `$2y$` and takes the cost from
the hash, not from `TOKEN_BCRYPT_ROUNDS`. The Go hash and the node verifier are the same
algorithm with the same encoding, so **no runtime scripting or format translation is needed:
importing the hash into `hashedPassword` is enough** for the existing login to accept the
original password. The repository proves it with a fixture generated by Go
(`tests/unit/services/project-import.password.test.ts`).

**What a CDM import does today.** A user imported with `findBy: email` becomes a global user
plus an email authentication method with `providerData: {}` and `isVerified: false`
(`user-provision.cdm-entity.ts:125,149,168`); the contract says so in
`sync-project-cdm.graphql:42` ("global passwordless email authentication method") and the docs
say imports "never create ... passwords". The only way for such a user into a project app is the
magic link: `requestProjectEmailMagicLink` (`project-oauth.handler.ts:485`), filtered per app by
`enabledProviders` (`:503-504`).

**Where the hash goes today, and why it is the wrong place.** The adopter's ETL puts it in
project-user metadata, `cdmSource.legacy.passwordHash`. That is importer-owned JSON stored on
`project_users.metadata`: it is not a credential store, nothing verifies against it, it is
exported back out with the rest of `cdmSource` (`extractProjectUserMetadataForCdmExport`), and
the only protection is that `passwordHash` is on the search-index denylist
(`search-document.lib.ts:9`).

**Where an inline import lives while it runs.** The document is stored whole in
`project_sync_jobs.payload` (`projects.handler.ts:229-236`), the worker reads it back from
there, and `GET .../sync/jobs/{jobId}/payload` returns it. The payload is unredacted today (it can
already carry BYOK `clientSecret`, `storage.middleware.ts:60`). A by-reference document is an
object that is deleted when its job ends (ADR 0009).

## Decision

### (a) Import a pre-hashed bcrypt credential: this change

_Amended by [0011](./0011-password-as-a-scoped-credential.md): rules 3 to 6 and 8 (where the hash is stored, who owns it, which identities may receive it, the counters) are replaced by a per-project credential. Rules 1, 2 and 7 stand._

1. **A per-user `password: { algorithm: 'bcrypt', hash }`** on `UserCdmInput` (GraphQL) and
   `users[]` (REST and the shared document schema), both strict. `algorithm` is the literal
   `bcrypt`. `hash` must match `^\$2[aby]\$(\d{2})\$[./A-Za-z0-9]{53}$` and its cost must be
   within **[4, 15]**. The bounds are constants (`CDM_BCRYPT_MIN_COST`,
   `CDM_BCRYPT_MAX_COST`), not environment keys: 4 is bcrypt's own floor, and 15 is a ceiling on
   what a document can make every later sign-in cost (§ Security notes). That is a security limit
   a reviewer should see change, not a deployment-sizing knob like `CDM_IMPORT_MAX_ENTITIES`.
   Every refusal names the position and the rule and never the value.
2. **Email-identified users only.** The credential lives on the email authentication method, so
   `password` with any other `key.findBy` is a **validation error**, not a warning. A warning
   would let an ETL believe passwords were imported for users who then cannot sign in. The
   rule, like the format, lives in `validateSyncInput`, which the inline start, the by-reference
   worker and the GraphQL path all run.
3. **Stored where login reads it.** The hash is written to `providerData.hashedPassword`, the
   field and shape `changePassword` writes, so `auth.handler.ts` login works unchanged. Beside it
   the import writes **`providerData.passwordSource: 'cdm-import'`**, a provenance marker.
4. **Ownership is forward-only: the legacy system owns an imported credential during the
   unverified migration window; verification, or any Grant-side change, hands it to Grant.**
   While the marker is present **and the email method is unverified**, a later import of the same
   project owns the credential: a **different** hash replaces it (`passwordsUpdated`), an
   **identical** hash is a no-op (`passwordsUnchanged`). A user who changes their legacy password
   after the first import must not keep the stale hash in Grant for ever.
   - **Verification is the handover.** Once the owner proves the mailbox (for example through the
     project OAuth magic link, which sets `isVerified: true` and leaves the marker), the
     credential is Grant's exactly as after a password change: an import skips it and counts
     `passwordsSkippedExisting`, writes nothing, whatever the marker says.
   - **Every Grant-side set, change or reset removes the marker** (`changePassword` and
     `resetPassword` in `user-authentication-methods.service.ts`, the only two paths that write
     `hashedPassword` to an existing method; there is no administrator path), so ownership passes
     to Grant and imports never touch the credential again.
   - A password with no marker (set in Grant before any import) is never overwritten
     (`passwordsSkippedExisting`). **An import never deletes a credential**: an absent
     `password` leaves the stored one alone.
   - **Cost, accepted:** a user who verified and then rotated their password only in the legacy
     system is not re-synchronized. They have a Grant login, and the recovery path is Grant's
     `resetPassword` or `changePassword`.
5. **Which identities an import may write a credential to.** The credential is global, so the
   project's document may only write one it has a claim to:
   - an identity **the import creates**, or
   - one **an earlier import of this project created** (the user carries this project's
     `metadata.cdmImport`) whose email method is **unverified** and either has no password or
     carries an import-marked one (replacement under rule 4), and
   - only ever through an **Email** method: an identity found through GitHub or Google is a real
     account that no import created, so it is skipped and its OAuth `providerData` is never
     written (the passwordless Email method an import adds beside a GitHub identity stays
     passwordless).

     Everything else is left untouched and counted in `passwordsSkippedExisting`, with one
     aggregate warning on the result: a user who registered in Grant, signed in with GitHub or
     Google, was provisioned by another project, or verified the address. Without this rule a
     project administrator could set a known password on someone else's global account
     (§ Security notes 1).
6. **Replace mode keeps credentials.** Credentials belong to the global user and its email
   authentication method, which no replace teardown touches (user provisioning's `teardown` is a
   no-op, and no import repository teardown names an authentication method). Tests assert that a
   `replace` re-import leaves the credential and issues no authentication-method write.
7. **Where the hash may exist.** In the credential store; in the document while the job runs; and
   nowhere else.
   - Never in `metadata`, `searchable` or the search document, in audit values, in event payloads
     (entity events are suppressed during an import, and the completion event carries counters
     only), in logs, or in a message.
   - **Inline job payload (a deviation from "redact before persisting").** The worker reads the
     document from `project_sync_jobs.payload`, possibly in another process, so the hash cannot
     be removed before it is stored without losing it. It is instead **removed in the same
     transaction as the transition to a terminal state** (`COMPLETED`, `FAILED`, and `CANCELLED`
     for a pending job), replaced by `[redacted]`. The `/payload` answer **always** redacts, so
     a job that still holds the hash does not hand it out. A redacted payload that is
     re-submitted fails validation (`[redacted]` is not a bcrypt hash) instead of silently
     importing without credentials. A job that never reaches a terminal state holds the hash
     until it does (§ Security notes 5).
   - **By-reference imports.** The uploaded object is deleted at every terminal state, as
     ADR 0009 already decides, and is not read through `/payload`.
8. **Result.** `SyncProjectResult` gains `passwordsImported`, `passwordsUpdated`,
   `passwordsUnchanged` and `passwordsSkippedExisting`, carried into the completion event and
   the audit entry as counters.

### (b) Email and password as a per-project-app sign-in option: follow-up slice

_Amended by [0011](./0011-password-as-a-scoped-credential.md) § 5: password sign-in is its own `password` value of `enabledProviders` (replacing the `allow_password_sign_in` boolean below), verified against the project's own credential only, never the global Grant password._

Not built here; this is the shape the slice is held to.

- **Setting.** A boolean on the project app, `allow_password_sign_in`, default `false`,
  following the existing per-app boolean `allow_sign_up` (`project-apps.schema.ts:32`), surfaced
  where `allowSignUp` is (GraphQL, REST, dashboard). It is an addition to
  `enabledProviders` including `email`, not a replacement for it.
- **Verification.** The same stored hash and the same `verifySecret`. A user with **no
  password set** gets the magic link only, and the response must not reveal which case it is
  (generic failure, and a dummy compare so timing does not either).
- **Result of success.** The one-time authorization code the magic-link callback already issues
  for the app, **never a platform session**.
- **Rate limiting and lockout.** Reuse the auth-route limiter (`rate-limit.middleware.ts:98-104`),
  which is per client address. **There is no per-account lockout to reuse**:
  `AUTH_MAX_FAILED_LOGIN_ATTEMPTS` and `AUTH_LOCKOUT_DURATION_MINUTES` are defined
  (`env.config.ts:149,152`) and nothing reads them. Per-identity throttling shared with platform
  login is a prerequisite of this slice and enabling the setting without it is not acceptable.
- **MFA.** When the user has an active enrolment (or the app or project requires it), a correct
  password yields a step-up requirement as `computeRequiresMfaStepUp` does for platform login
  (`auth.handler.ts:66-76`), and no code is minted until it is satisfied.
- **Verification state.** An imported identity is unverified. Signing in with the password must
  not mark the address verified (the magic link stays the proof of mailbox), and the token the
  app receives must say `email_verified: false`. Whether an app may accept an unverified
  identity at all is the app's decision through that claim. To be confirmed in review of the
  slice.
- **Optional rehash-on-login.** After a successful verification of a hash whose cost is below
  `TOKEN_BCRYPT_ROUNDS`, store a fresh hash and clear the import marker's meaning accordingly.
  **Not implemented here**: it changes the platform login path and belongs with (b)'s login,
  where both can share one verify-and-upgrade function with its own tests.

## Alternatives considered

- **Runtime hash-verification scripting** (adopter-supplied code that verifies an unknown format
  at login). Rejected. It puts arbitrary code on the login path, and it is unnecessary: the legacy
  algorithm is the one Grant already stores and verifies.
- **Lazy migration by calling the legacy system at login** (a Cognito user-migration trigger).
  Rejected. It keeps the legacy system on the login path (availability, and the plaintext
  password crossing to it), and users who never sign in are never migrated, so the legacy system
  can never be retired.
- **Forced reset or magic link.** The status quo, and what the adopter is trying to avoid.
- **Keep the hash in metadata and verify against it.** Rejected. Metadata is not a credential
  store: it is exported, searchable-adjacent and read by anything that reads metadata. It would
  also need a second verification branch in every login path.
- **A second credential field** (for example `legacyPasswordHash`) with its own verifier. Rejected
  for the same reason: the formats are identical, so one field and one verifier keep one place
  where a credential is checked and one place where it is protected.
- **Never overwrite an existing password; or overwrite any.** Rejected for the provenance rule:
  the first strands a user on a stale legacy hash after they change it in the legacy system;
  the second lets an import clobber a password the user set in Grant.

## Consequences

- The legacy system owns an imported credential until the owner verifies the address or sets,
  changes or resets the password in Grant. From then on Grant owns it. An adopter should stop re-importing
  credentials once project apps sign in through Grant.
- An adopter whose ETL already wrote `passwordHash` into metadata has copies in
  `project_users.metadata` and in later exports. Grant does not scrub what it was sent; the
  ETL should stop sending it and the adopter should clear it.
- Imported identities stay `isVerified: false`. Platform login accepts an unverified method only
  for the verification window after the method was created (`auth.handler.ts:455-466`), so an
  imported credential stops working for **platform** login when that window passes. That is
  intentional here and a decision for (b) for project apps.
- Platform login applies no password policy at login, so a legacy password that Grant's policy
  would refuse still works; the policy applies when it is next changed.
- The `ProjectSyncJob` stored payload is rewritten at terminal states when it holds a hash
  (one extra `UPDATE`, only for such jobs).
- The web import result card does not show the four counters yet.
- Rehash-on-login is a follow-up, so a cost-4 legacy hash stays cost 4 until (b).

## Security notes (for the security review)

1. **Identity eligibility is the control against cross-tenant takeover** (_superseded by [0011](./0011-password-as-a-scoped-credential.md) § 8: the credential no longer lives on the shared identity_). CDM already lets a
   project administrator attach project membership to any global user by email. A credential is
   different: it is global, and with it the administrator could sign in as that user. The import
   therefore writes a credential only where it created the identity, or where an earlier import
   of the same project did and nobody has since verified or given it a password (rules 4 and 5).
   The tests cover a Grant registrant, a GitHub user, an identity of another project and another
   project's imported credential. Residual: a project administrator can still **pre-claim an
   address that has no Grant identity yet**, with a password only they know (account
   pre-hijacking). The same administrator can already pre-claim the identity itself; the
   credential adds that they can sign in to the **platform** while the verification window is
   open. Mitigations: the method is unverified, the window is bounded, and the real owner
   recovers through password reset, which clears the marker and invalidates sessions.
   Second point, **decided**: replacement of an import-marked credential stops at verification.
   Left open, a project administrator could set a known password on a verified global account the
   import created (the owner verified through the magic link and never changed the password in
   Grant), which is the takeover this record exists to prevent. Rule 4 therefore skips a verified
   method. The cost is stated there: a user who verified and then rotated only the legacy password
   is not re-synchronized, and recovers through Grant's reset or change.
   Also noted, and not introduced here: the email lookup used to find an existing identity
   (`findByEmail`) matches with `ILIKE`, so `_` and `%` in an imported address act as wildcards;
   the credential rules above still compare the exact address against the project's own
   provisioning record, so a wildcard match is skipped, not written.
2. **Cost ceiling.** The cost is read from the hash and `compareSync` blocks the event loop, so
   an unbounded cost in a document would turn every sign-in attempt into a stall. The ceiling
   is 15 (about 2^15 rounds), the floor is bcrypt's 4.
3. **The hash is never echoed.** Refusals carry the field path and a fixed rule. The by-reference
   worker's refusals are stored on the job row and published as `project_sync.failed`, so they
   name positions, never keys or hashes. Residual: graphql-js reports a malformed **container**
   (for example `password` given as a bare string instead of an object) with the offending value
   in its coercion message, which goes to the caller who sent it; the REST body schema does not.
4. **Inventory of where a hash can exist.** The credential store (`user_authentication_methods
.provider_data`); the stored job payload while a job is pending or running; the by-reference
   object until its job ends; the request body in flight and in whatever the adopter's proxy logs
   (outside Grant). It is not in the pre-import rollback snapshot or an export (the exporter
   emits no `password`), in audit entries, events, webhook payloads (the existing redaction
   matches `password` and `hashedPassword` keys at any depth), search documents or logs.
5. **Payload retention window.** A job that never reaches a terminal state (a crashed worker; no
   reaper exists yet, ADR 0009 part B) holds the hash in its row until it does. This is the same
   class of exposure as BYOK `clientSecret`, which is stored in plaintext in the same payload
   and not redacted at all today; that is out of scope here and worth its own record.
6. **Comparison.** A re-import compares the stored and incoming hash in constant time. An
   attacker who can import is a project administrator, so this is hardening, not a boundary.
7. **Concurrency.** An import reads an identity's `providerData` and writes it back like every
   other writer of that field. A user changing their password in the instant between is the same
   race `changePassword` and `resetPassword` already have with each other; the window is one
   user's apply step.
8. **Weak legacy hashes.** Cost 4 is accepted: it is the adopter's existing credential, and
   refusing it would block the migration. Rehash-on-login (b) is what upgrades it.
