### Fan-out {#fan-out}

Every slice above is genuinely independent at the file level — none of them share a file with another, so nothing here _requires_ serialization the way `apps/api` pass 1's slices 5–7 required waiting on slice 4's deletions. The decision to run them serially anyway is a **single-reviewer** call, mirroring pass 1's slices 1/2/4: with one human doing async light review, parallel slices compete for review attention and create rebase churn for no measurable gain on a story this size (7 slices, no cross-slice blocking dependency). If a second Frontend implementer becomes available mid-story, slices 2 through 7 can be pulled out of the linear `gh stack` chain and opened directly against `feat/web-code-quality` in a second worktree — nothing about their content assumes serial execution, only the review process does.

The one fan-out that **is** load-bearing, not just a nice-to-have: slice 1's Security review must be a separate pass by Senior Security, not evidence the Frontend author gathers about their own fix. This is within-slice fan-out (a reviewer reading the same tree the author wrote, no worktree needed) and it must happen before slice 1 merges — not folded into the story→`main` gate 4 review, where a BLOCK verdict would arrive after six more slices have stacked on top of it. This is exactly the failure pass 1 hit on its `CacheHandler` slice (correction 19): an author's own security pass reported clean, and an independent pass on the same commit found a reachable fail-open.

## Slice detail

### 1 — Tier 0.1 `SessionRestoreGate` fix + the two uncommitted audit files · security-full

Land the two files the audit already produced, uncommitted in the working tree:

- `apps/web/vitest.config.ts` — the 2-line `oxc.jsx.runtime: 'automatic'` fix that lets Vitest parse JSX at all. Without it, `apps/web` has zero possible component-level test coverage — every other slice in this story that touches a component depends on this landing first.
- `apps/web/components/providers/session-restore-gate.test.tsx` — 8 characterization tests written pre-fix, including the one that caught 0.1.

Then fix [`components/providers/session-restore-gate.tsx:65,71,128`](../apps/web/components/providers/session-restore-gate.tsx): after `clearAuth()`, the gate must not silently re-authenticate via the still-valid refresh cookie. Two concrete gaps, both must close:

- `:65,71` — resetting `restoreStatus` to `'idle'` on `clearAuth()` currently re-fires the same restore-trigger effect used on first mount, so an explicit logout and a cold boot are indistinguishable to the gate. The fix needs to tell them apart — e.g. an explicit `clearAuth()` should not re-arm automatic cookie-based restoration the way a fresh page load does.
- `:128` — the render branch (`restoreStatus === 'done' && !publicPath`) does not also require `auth` to be truthy, so protected content can render for at least one pass before step 4's outcome (revoked vs. still-valid cookie) is known. Gate the render on `auth` too.

**Scope decision, made here rather than left open:** this is a client-only fix. The findings doc leaves two remediation shapes open — the gate proactively calling `logoutSession()`, or the gate simply not re-triggering automatic restore after an explicit `clearAuth()`. Both are achievable with existing client code (the revoke mutations already exist and are called by every current `clearAuth()` site); neither requires a new `apps/api` endpoint or contract change. **No Backend slice is needed for 0.1** — if implementation surfaces a reason a server-side change is actually required, stop and bring it back to Principal Engineer rather than absorbing it into this slice.

**On the existing characterization tests**: unlike `apps/api` pass 1's `CacheHandler` slices, where characterization tests had to stay byte-identical because those slices were pure refactors, this is a bug-fix slice. At least one of the 8 existing tests documents the _current buggy_ behavior directly and is expected to flip to asserting the fixed behavior — that test changing is correct here, not a signal to stop. Add a regression test for "does not re-authenticate when the cookie was never revoked" if the existing 8 don't already isolate that exact case tightly enough to serve as one.

**Review**: Senior Security reviews independently of the Frontend author — see [Fan-out](#fan-out). Blocking; PR does not merge without this sign-off, regardless of how much evidence the author attaches.

### 2 — Tier 0.2 + 0.3 (non-security bugs)

**0.2** — none of the six RBAC list viewers (`GroupViewer`, `RoleViewer`, `PermissionViewer`, `TagViewer`, `UserViewer`, `ProjectViewer` — see the table in [findings 0.2](../docs/contributing/code-quality/web.md#02-rbac-list-viewers-drop-query-errors-contradicting-the-documented-intent-next-to-them)) destructure `error` from their query hook, so a permission-denied response renders as a silent empty list instead of the inline error `lib/apollo-client.ts:46-59`'s comment says these six are exempted from the global redirect specifically to show. Wire `error` through each viewer and render it. This changes error-surfacing behavior on RBAC-scoped queries (not just adding a missing UI state) — reviewers should read it as a UX/behavior change, not a pure bug fix, per the brief's risk flag.

**0.3** — [`hooks/tags/use-tags.ts:37-54`](../apps/web/hooks/tags/use-tags.ts) drops the server-computed `hasNextPage`; its only consumer, [`hooks/tags/use-paginated-tags.ts:47`](../apps/web/hooks/tags/use-paginated-tags.ts), recomputes it from `page * pageSize < totalCount`. Return `hasNextPage` from `use-tags.ts` and delete the recomputation in `use-paginated-tags.ts`. Same defect class as `api.md`'s 0.2 (a value computed once, discarded, and recomputed a second way) — client-side, lower severity, same fix shape.

Each bug gets its own regression test; Senior QA authors or reviews both per the brief.

### 3 — Guardrails: hooks-only data-fetching boundary + import-discipline

Owned by Architect because there is no existing `apps/web` layering doc to extend — `AGENTS.md` covers `apps/api`'s handler → service → repository boundary but says nothing about `apps/web`. Two deliverables:

**1. Write the boundary down.** Of 831 files, 6 of 7 direct `useQuery`/`useMutation`/`useLazyQuery`/`useSubscription` callers already live in `hooks/**` — this is a real, load-bearing convention today, just not committed to paper. Add a section to `AGENTS.md` (sibling to the existing "API app layer boundaries" section — the file already documents `apps/api`'s layers this way, so extending it in place is more consistent than a new standalone doc) stating: `app/`/`components/` consume `hooks/`; `hooks/` is the only place Apollo operations (`useQuery`/`useMutation`/`useLazyQuery`/`useSubscription`) and `*Document` imports from `@grantjs/schema` are wired, except two named, justified exceptions (below).

**2. Enforce it.** `no-restricted-imports` (or an equivalent scoped rule) in the root `eslint.config.mjs`, forbidding `@apollo/client` and `@grantjs/schema` `*Document` imports outside `hooks/**` and the two exempted files. Follows the same `files:`-scoped-block pattern the file already uses for `apps/api/**` (see e.g. `eslint.config.mjs:140,168,176`) — add `apps/web/**` blocks alongside them, not a separate config file.

**Fix the two genuine gaps** so the new rule passes clean on landing:

- [`app/[locale]/auth/mfa/page.tsx:6,8-11,35-39`](../apps/web/app/%5Blocale%5D/auth/mfa/page.tsx) calls `useMutation` directly for 3 operations with no wrapping hook anywhere. Add a hook (`hooks/mfa/` — a new file, since `use-mfa-mutations.ts` wraps a different, `My*`-prefixed set for the settings flow, not these).
- [`app/[locale]/auth/project/email/page.tsx:60-72`](../apps/web/app/%5Blocale%5D/auth/project/email/page.tsx) inlines a raw `fetch()` where [`lib/project-oauth-api.ts`](../apps/web/lib/project-oauth-api.ts) already wraps the same REST surface for 2 sibling pages. Add a 5th function there instead of a second implementation.

**Decide, don't fix, the two borderline sites** — `mfa-step-up-dialog.tsx`'s second Apollo client and `notification-bell.tsx`'s imperative preview query both have a plausible rationale the audit didn't reject (step-up re-auth needing to avoid the shared client's refresh-interceptor recursion; an on-demand popover preview not being a subscribed list). Per the brief's non-goals, they're **not** being "fixed" — both stay, as explicit, named, documented exceptions in the lint rule (not silent `eslint-disable` comments), so the rule's exception list is itself the record of the decision.

**Resolve 3.6 here, not as a separate Tier 3 slice** — it's the same category of decision as the two bullets above (which package/pattern is the sanctioned one for a given kind of import), so it belongs with the rest of the import-discipline rule rather than split into slice 7. [`components/features/permissions/permission-types.ts:1`](../apps/web/components/features/permissions/permission-types.ts) imports `permissionConditionSchema` from `@grantjs/core` directly — the only such site. Check whether `@grantjs/schema` re-exports it: if yes, migrate the one import and the rule can ban `@grantjs/core` imports from `apps/web/**` outright; if no, the decision is that `apps/web` may reach `@grantjs/core` for zod schemas that aren't GraphQL-codegen'd, and the rule should say so explicitly rather than leave the one site as an unexplained exception.

### 5 — `usePaginationProps` extraction

14 sites (`components/features/*/​*-pagination.tsx`), each a 9-line file with a 6-line identical body (4 store-selector reads + `Math.ceil` + return) differing only in which `useXStore` is passed. Extract `usePaginationProps(useXStore)`; each call site collapses to:

```tsx
export function GroupPagination() {
  return <Pagination {...usePaginationProps(useGroupsStore)} />;
}
```

No behavior change. This is the one Tier 2 item the brief pre-approves outright — sized against the call site (6→2 lines × 14), not against total pattern size.

### 6 — `tags.store.ts` investigation: Tier 2 factory decision + Tier 3 URL-parsing decision

**Not a "collapse the 13 stores" slice.** The brief is explicit that store/hook-factory extraction is not pre-approved — open the hardest instance first and decide, the same rule pass 1 learned the hard way on `resolveDelete()` and the add/remove wrappers (correction 14 / rubric rule 6: a repeated _shape_ doesn't imply an extractable helper until you check the shape actually recurs cleanly).

`tags.store.ts` is deliberately the one opened, because it's the one place the 13-store family stops being byte-identical after normalizing the entity name:

- **Extra fields**: `tags.store.ts` carries `selectedTagIds`/`hideSyntheticEntities`, which `groups.store.ts`/`roles.store.ts` don't have. Decide whether a generic factory can absorb this cleanly (e.g., an optional extension-slice parameter) without the factory's config surface growing larger than the code it would replace. If it can't stay small, that's the answer — record "no factory" as the decision, not a fallback.
- **Divergent URL-parsing**: [`stores/tags.store.ts:105-106`](../apps/web/stores/tags.store.ts) uses `parseInt(params.get('page') || '1')` with `isNaN` guards; every other URL-synced store uses `Number(params.get('page')) || 1` (e.g. [`stores/groups.store.ts:117-118`](../apps/web/stores/groups.store.ts)). **Check before aligning blindly**: the two are not behaviorally identical for a malformed-but-partially-numeric value — `Number('12abc')` is `NaN` (falls back to `1`), `parseInt('12abc')` is `12` (does not). Confirm which behavior is actually wanted for a `?page=` query param before switching `tags.store.ts` to match the majority; if `parseInt`'s tolerance turns out to be intentional (or just as defensible), record that instead of "fixing" it to match.

**Outcome, either way, gets recorded** (`CONCEPTS.md` or inline, per the brief's acceptance criterion): if the two hardest instances turn out compatible with a small factory, build it in this slice — do not size it against all 13 files and assume the rest follow trivially; if not, document why and leave the factory as an explicit follow-up rather than an implied one. Detail-scoped stores (`group.store.ts`, `role.store.ts`, `user.store.ts`, etc.) are out of scope regardless of the outcome here — the brief's non-goals note they were never verified near-identical.

### 7 — Remaining Tier 3 decisions

Each gets an explicit, recorded decision — the acceptance criterion is met by the decision, not necessarily by a code change:

- **URL-synced pagination on the 4 stores missing it** (`api-keys`, `project-apps`, `webhooks`, `project-sync-jobs` don't implement `initializeFromUrl`; the other 9 do, over an identical page/limit/search/sort/totalCount shape). **Decision: defer implementation.** Rolling it out changes page-load/routing behavior for four more entity views — bigger than a docs-only decision, and not required by any Tier 0 bug. Record the decision and rationale in `CONCEPTS.md`; track as a follow-up if someone wants the consistency later.
- **Raw errors / `console.*`**: `AGENTS.md`'s bans are scoped to API source and runtime adapter code today, not `apps/web`. **Decision: status quo affirmed, not resolved.** Introducing a structured client-side error type or a Sentry-style logging sink is a bigger design conversation than this story (the brief's non-goals already exclude a formal domain-exception hierarchy for the same reason) — record that `apps/web` continues using raw `Error`/`console.*` pending a future decision, rather than silently leaving the question open.
- **"Workspace" UI term**: doc note only, per the brief's non-goals — one line in `CONCEPTS.md` or `AGENTS.md` noting `Account`/`AccountType.Personal | Organization` is the contract term and "workspace" is a UI-only synonym introduced in `workspace-switcher.tsx` and 4 sidebar i18n labels, 0 occurrences in `@grantjs/schema`. No rename.

## Judgment calls for gate 2 {#judgment-calls}

Flagging these for the human reviewer before implementation starts — none contradict the brief, but each is a call I made filling in a gap the brief left to stack-planning time:

1. **0.1's fix is scoped as client-only**, choosing between the findings doc's two open remediation shapes implicitly (not re-litigating "should the gate call `logoutSession()`" vs. "should it just stop auto-retrying" — that's left to whoever implements slice 1, with the constraint that either shape must not require a new backend endpoint). If implementation finds neither shape actually closes the gap without a server-side change, that's a stop-and-return-to-Principal-Engineer moment, not something to absorb into slice 1's scope.
2. **`styles/tokens.ts` vs. `tailwind.config.ts`'s inline duplicate**: I decided to keep the tailwind config's copy and delete `styles/tokens.ts`, plus correct `react-and-web.mdc:38`'s now-wrong claim about which file is the source of truth. This is the more consequential of the two dead-surface picks the brief left open (the other, `eslint-config-next`, has no live behavior either way).
3. **Tier 2 store/hook-factory extraction is explicitly not pre-sized in this plan** — slice 6 is scoped as an investigation with a decision recorded either way, per the brief. It is plausible the outcome is "no factory," in which case slice 6 is a documentation-only PR. That is an acceptable outcome, not a failed slice.
4. **Tier 6 coverage extension past `SessionRestoreGate`** (the brief's suggested-roles section names `lib/apollo-client.ts` as the QA-owned next target) is **not** in this plan's acceptance criteria and is **not** a slice here — it's listed as a follow-up. The brief's role description reads as QA's standing remit rather than a bullet in "Acceptance criteria," and adding it as an eighth slice would extend the story past what was actually approved. Flagging in case the intent was for it to be in-scope now.
5. **Slices 2–7 are sequenced as a single linear `gh stack` chain** even though every one of them is file-independent of the others (see [Fan-out](#fan-out)). This is a single-reviewer-bandwidth call, the same one pass 1 made for its slices 1/2/4 — reversible mid-story if a second implementer joins.
