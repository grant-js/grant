## Objective

A webhook receiver that mirrors Grant into another system can name the entity a delete or revoke event removed, and for a removed or deleted **user** can name the external key the CDM import attached to that person, from the event alone, after Grant no longer holds the user or the membership. The external envelope already keeps an identity-only `data.before` for delete and revoke events (since v1.18.1); this story pins that with a test and adds the one thing still missing: the user's external keys on `user.deleted` and `project.user_removed`, without any email, name or hash.

## What is already true, and what is missing

Read from `origin/main` at `4f9446f4`.

**Part 1 (`data.before` survives for delete and revoke events) is already true.** `redactEventData` projects the internal `before` through `projectIdentity` for every event type (`apps/api/src/lib/webhooks/webhook-redaction.lib.ts:117-128`). `projectIdentity` (`:90-109`) copies only the keys in `EVENT_IDENTITY_KEYS` (`packages/@grantjs/schema/src/events/event-envelope.ts:24-44`) and only when the value is a string, number, boolean or `null` (`:78-80`, `:100`); `name` is dropped for events about a person (`isUserEvent`, `:70-76`, applied at `:124`). The envelope sets `data` from it (`apps/api/src/lib/webhooks/webhook-envelope.lib.ts:23`) and the stored payload reaches it unchanged (`apps/api/src/lib/events/event-log-mapper.lib.ts:35`).

Of the 20 delete, revoke, remove and unlink types in the catalog (`packages/@grantjs/schema/src/events/event-catalog.ts:97-162`), **18 publish a `before` that survives with identity keys today**:

**What is missing for part 1:** a test that pins it per type. `apps/api/tests/unit/lib/webhooks/redaction.test.ts` covers the projection in general (`:32`, `:141`, `:172-262`) and two e2e files assert `before` keys for a few types (`webhooks-cascade-lifecycle.e2e.test.ts:266-267`, `webhooks-notifications.e2e.test.ts:375-377`); nothing walks the catalog, so a new delete type that publishes no `before`, or a change to `EVENT_IDENTITY_KEYS`, regresses silently. The docs table (`events-webhooks-notifications.md:173-189`) is already complete for the 18.

**What is missing for part 2:** `user.deleted` carries `id` and `project.user_removed` carries `id`, `projectId`, `userId`. Neither carries an external key. `projectIdentity` could not carry one even if the services stored it: it drops every non-primitive value (`webhook-redaction.lib.ts:100`) and the allowlist has no such key.

### Findings that shape part 2

These came from reading the code, not from the request, and each changes a criterion.

1. **The marker's `externalKey` is the e-mail address for most imported users.** The CDM import keys a user either by key (`findBy: key`, `externalKey` is a source-system id) or by e-mail (`findBy: email`, `externalKey` is the lower-cased address: `apps/api/src/lib/cdm/cdm-document.schemas.ts:286`, `user-provision.cdm-entity.ts:68`, `:111`, `docs/core-concepts/cdm-import-export.md:189-191`). A migration importer keys a person by address whenever they have a valid, unique one, so `metadata.cdmImport.externalKey` is personal data for those users, and the "never an email" rule forbids copying it. The id a receiver needs for them is the importer's own, which the reference migration importer records as `metadata.legacy.id` under `cdmSource` (the importer-owned payload, `cdm-import.constants.ts:12`, merged at `user-provision.cdm-entity.ts:130-133`, `:241-244`, and copied to the membership row at `expand-cdm-sync-input.lib.ts:187` and `user-assignment.cdm-entity.ts:265`).
2. **A reused identity is, by construction, an e-mail-keyed one.** `findBy: key` only matches a global user carrying **this project's** marker (`users.repository.ts:115-135`), so an identity the import reused is one resolved by address (`applyEmailIdentity`, `user-provision.cdm-entity.ts:193-228`). Its global metadata is never changed; the membership row carries this project's marker (`mergeProjectUserCdmMetadata`, `project-users.repository.ts:98-`, grant #568) and the importer payload under `cdmSource`. So for exactly the case the request calls a requirement, the marker's key is an address. Criterion 2 can only be met from the row's `cdmSource.legacy.id`, or not at all.
3. **One `user.deleted` fans out to every project the user belongs to** (`projectIds`, `users.service.ts:272-275`, `webhook-dispatcher.consumer.ts:21-23`) and the body is built once per delivery from the stored event (`webhook-delivery.service.ts:115`). A flat list of keys would show project A's receiver the key project B's importer attached. The keys must be filtered per subscription project.
4. **A global user's marker names one project**, and the membership row's marker (written by #568 for every user an import assigns) names the project of that row. Rows written before #568 and never re-imported carry no row marker.

## Acceptance criteria

- [ ] **Part 1 stays true and is pinned.** A catalog-driven unit test (`apps/api/tests/unit/lib/webhooks/`) lists each of the 18 delete, revoke and remove types above with the internal `before` its service publishes and asserts the external `data.before` equals exactly the identity keys in the table; and asserts that every `EVENT_TYPES` entry matching `*_deleted`, `*_revoked`, `*_removed` or `*_unlinked` is either in the table or in an explicit exception list with a reason (`tag.unlinked`: ids stay in `data.after`; `user.sessions_revoked`: bulk, no single entity), so a new delete type fails the test until someone classifies it. The existing e2e `before` assertions stay as they are. No change to `EVENT_IDENTITY_KEYS`, to the ids-only rule, or to `tag.unlinked`.
- [ ] **`user.deleted` and `project.user_removed` carry `data.before.externalKeys`**, a list of `{ projectId, externalKey }`, one entry per project, in the external envelope. Name, shape and the choice of per-entry `projectId` are justified in the stack plan's named contracts (`externalKey` is the CDM's word: `metadata.cdmImport.externalKey`, `resolveCdmExportExternalKey`; the plural list because a person can be marked by more than one project). The list is **always present** on these two types, empty (`[]`) for a Grant-native user or when no key qualifies, so a receiver tells "no key" from "Grant older than v1.20.2" (field absent).
  - **What qualifies as a key (recommended option B, Gate 1 question 1).** For a project, the entry's `externalKey` is: the membership row's `metadata.cdmImport.externalKey` when it is **not e-mail-shaped**; otherwise the importer-declared id `metadata.cdmSource.legacy.id` (a string, trimmed, 1 to 255 characters, not e-mail-shaped) from the row; when the row has neither, the same two reads on the global user's metadata if its marker names that project. Row wins over the global user (the project-scoped read already merges them that way, `docs/core-concepts/cdm-import-export.md:398`). E-mail-shaped means the pattern the importer itself uses (`user-provision.cdm-entity.ts:68`, `/^[^\s@]+@[^\s@]+\.[^\s@]+$/`) **or any value containing `@`**; a value that fails is skipped, never truncated or transformed. Nothing else from `cdmSource` is read: not `legacy.email`, not names, not roles, not the rest of the snapshot. One entry per `projectId`; duplicates dropped.
  - **When the keys are read.** `user.deleted`: in `UserService.deleteUser` at the point where `resolveLinkedProjectIds` already reads the memberships, **before** the event is published and before the delete (`users.service.ts:272-293`: the event goes in first because `event_log.subject_user_id` references `users.id`). The global user's metadata is `oldUser.metadata` (already loaded, `:234`); the membership rows come from one new read next to `getUserProjectIds` (`project-links.repository.ts:142`), live rows only, in the same transaction. Hard and soft delete behave the same. `project.user_removed`: in `ProjectUserService.removeProjectUser` from the row the repository returns for the delete it just made (`project-users.service.ts:471-482`; the slice confirms the returned row carries `metadata`, and the row marker is therefore read **after** the delete from the returned object, which is why the gone-after-removal marker is still available) and the global user read there (the user still exists after a removal). Only the removed project's entry is stored on this event.
  - **Per-subscription filtering (tenancy).** The stored (internal) `before.externalKeys` holds every entry. The external projection keeps only entries whose `projectId` is the subscription's project and drops the rest: `buildCloudEventEnvelope` takes the delivery's project (the subscription's own `projectId` column, which is also what the dispatcher matches on: `webhook-subscriptions.repository.ts:100-117`) and **fails closed**: without it, or for a subscription that names no project, `externalKeys` is `[]`. The projection copies `externalKeys` for these two event types only.
  - **No personal data.** The projection emits only `projectId` and `externalKey`; never an e-mail, a name, a hash, a fingerprint or any other `cdmSource` key. The `dropName` rule is unchanged. The key is an identifier from the source system: pseudonymous (it means something only next to that system's own data), not a profile field. State it in the docs and the changeset in those words, not "not personal data".
- [ ] **Unit tests (QA).** The key resolver (pure function in `apps/api/src/lib/`): marker key kept when not e-mail-shaped; e-mail-shaped marker falls back to `cdmSource.legacy.id`; e-mail-shaped `legacy.id` skipped; value with `@` skipped; row wins over global; global marker for another project ignored; Grant-native (no marker, no `cdmSource`) gives `[]`; hostile metadata (non-object `cdmSource`, `legacy` an array, `id` a number or an object, 10 kB string) gives `[]`; nothing but `projectId` and `externalKey` in the output. The projection: `externalKeys` filtered by subscription project; absent option gives `[]`; other event types never copy `externalKeys` even if a snapshot had one; the existing `projectIdentity` tests unchanged. Service tests: `deleteUser` reads before publishing (call order asserted) and the stored `before` carries the entries; `removeProjectUser` stores only the removed project's entry.
- [ ] **E2E (QA, needs Docker: host or desktop lane; the PR body says whether it ran).** On the existing webhook e2e harness (`apps/api/tests/e2e/scenarios/webhooks-*.e2e.test.ts`): (a) a user created by a CDM import with a key-keyed identity: `user.deleted` body carries `[{ projectId, externalKey }]` with the id and **no** e-mail, name or hash anywhere in the body (assert on the serialised body, not only on the field); (b) an **identity the import reused** (an existing user resolved by address, assigned by the import): `project.user_removed` body carries the entry from the membership row's `cdmSource.legacy.id`, and the address appears nowhere in the body; (c) a Grant-native user: `user.deleted` and `project.user_removed` carry `externalKeys: []`; (d) a user who is a member of two projects, each marked by its own import: the delivery to project A's subscription carries only A's entry and the delivery to B's only B's; (e) hard delete (`hardDelete: true`) carries the keys as soft delete does.
- [ ] **Event-catalog docs.** `docs/core-concepts/events-webhooks-notifications.md`: the `user.deleted` bullet (`:78`, it says the event "carries ids and timestamps only") and the two table rows (`:179`, `:186`) say what `externalKeys` is, when it is empty, that it is filtered to the subscription's project, that an absent field means Grant older than v1.20.2, and the pseudonymous-identifier wording; the CDM importer convention that `cdmSource.legacy.id` is surfaced is stated in `docs/core-concepts/cdm-import-export.md` next to the marker paragraph (`:398`). ## Non-goals

- Changing the ids-only rule for `data.after` / `data.delta` or the redaction patterns; adding any profile field to an event.
- Changing `tag.unlinked` (stays `after`-only for compatibility) or making `user.sessions_revoked` carry a `before`.
- The notification system (`user.deleted` is `webhookOnly`; `project.user_removed` notifications read names only, `notification-renderer.ts`, and are untouched).
- The receiver's side (reading the new field, resolving a removal by key): a follow-up in the receiver's repository once this is released and pinned.
- Writing a new marker or a new CDM field (option C of question 1), backfilling markers on rows imported before #568, or changing what an import writes.
- Keys for any event other than the two named; keys for `organization.member_removed` or `user.role_revoked`.
- Changing webhook signing, retry or delivery semantics.

## Decisions for Gate 1

1. **Where does the key come from?** The request says `metadata.cdmImport.externalKey`. For an e-mail-keyed user that value is the address, which the same request forbids, and an identity the import reused is always e-mail-keyed (findings 1 and 2), so the amended requirement for `project.user_removed` cannot be met from the marker alone.
   - **A. Marker only, e-mail-shaped keys skipped.** Smallest and safe; the list is empty for every e-mail-keyed user and every reused identity, so the receiver still cannot resolve the case the amendment exists for.
   - **B. Marker, then the importer-declared `cdmSource.legacy.id` (recommended; written above).** Reads one string from the importer-owned payload, with the same e-mail guard. Couples Grant to a documented importer convention (`legacy.id`), stated in the CDM docs. Meets the requirement for both created and reused identities, because the importer copies the user's metadata to the membership row.
   - **C. A first-class CDM field** (for example an optional external id on the user entry, stored under `cdmImport`), a separate upstream story on the import path, then this story reads it. Cleanest contract; users already imported have none until re-imported, so the receiver waits for a new import.
2. **Security bar.** `security-full` on the one slice (tenancy fan-out and personal data both apply) rather than the light bar the request suggested? Recommended: yes.
3. **Hard delete (erasure).** Include `externalKeys` when `hardDelete` is true? The outbox row outlives the erasure (the reason `name` is never stored). Recommended: include, because offboarding a deleted person is the purpose and the key is pseudonymous; the docs say so, and the event log's retention is not bounded in this repository (no job under `apps/api/src/jobs` touches `event_log`; the slice confirms). If no: omit on hard delete and say so in the docs.
4. **Rows imported before #568** and never re-imported carry no row marker; for a reused identity under option A the key is then missing, under option B it comes from the row's `cdmSource.legacy.id`, which those rows do carry. Accept that a missing key is possible and documented, or require a re-import first?
5. **One slice or two** (stack plan): recommended one, because part 1 needs only a test; see the stack plan for the seam if the diff is too large.
