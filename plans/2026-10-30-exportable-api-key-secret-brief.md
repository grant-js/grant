## Objective

A receiver that mirrors Grant into another system can carry a project user's API key into that system when the key is created or rotated in Grant. Today Grant keeps only a bcrypt hash and shows the secret once, so a key made in Grant can never reach the other system. When a project opts in, Grant keeps an encrypted copy of a project-user API key's client secret at create and rotate (the reversible primitive project OAuth connection secrets already use), tells the receiver that a key changed through a non-secret fingerprint, and hands the plaintext out only through the gated, audited credential export that already exists for passwords, as a second credential kind.

## What is already true, and what is missing

Read from `origin/main` at `42afcf0b`.

### How project OAuth connection secrets are encrypted, and with which key

- **Primitive.** `apps/api/src/lib/project-oauth-connection.lib.ts`: AES-256-GCM with a 12-byte random IV, the AES key derived from the configured key material by scrypt (`N = 16384, r = 8, p = 1`, 32 bytes) under a **fixed purpose salt** `grant-platform:project-oauth-connection-secret-encryption:v1`, chosen so the derived key cannot be the MFA one (the file's comment names the MFA purpose string it must not reuse). Output is three base64 strings `{ encryptedSecret, secretIv, secretTag }`, stored in `project_oauth_connections.encrypted_secret varchar(4000)`, `secret_iv varchar(255)`, `secret_tag varchar(255)` (`packages/@grantjs/database/src/schemas/project-oauth-connections.schema.ts`), on a table with the two tenant RLS policies.
- **Key.** `PROJECT_OAUTH_CONNECTION_ENCRYPTION_KEY` (`packages/@grantjs/env/src/schema.ts:170`, `apps/api/src/config/env.config.ts:336-339`), resolved at point of use through `ISecretResolver` (ADR 0004): `ProjectOAuthConnectionService.requireEncryptionKey` (`apps/api/src/services/project-oauth-connections.service.ts:42-48`) throws `ConfigurationError` when it is empty, so a write fails closed; a decrypt failure is also a `ConfigurationError` naming the variable, never the material (`:184-197`). ADR 0008 rule 5 records the primitive and **rejects reusing `AUTH_MFA_SECRET_ENCRYPTION_KEY` "to isolate rotation blast radius"** (`decisions/0008-per-project-oauth-connections.md:27,42`). The variable is declared in 20 places (env schema, `apps/config` metadata and schemas, `deploy/aws` env file, props and a leak test, `docker-compose.e2e.yml`, `.env.test.example`, four docs pages); a sibling variable follows the same list.
- **What is missing.** The lib is written for one purpose: the salt is a module constant and the two functions are named for OAuth connections. Nothing encrypts an API-key secret; nothing decrypts anything for an export.

### How the D21 credential export works

- **Surfaces.** GraphQL `exportProjectUserCredentials(input: { scope, userIds, kinds })` (`packages/@grantjs/schema/src/schema/project-users/queries/export-project-user-credentials.graphql`) and REST `POST /api/users/credentials/export` (`apps/api/src/rest/routes/users.routes.ts:152-177`, `Cache-Control: no-store`), both gated at the transport by **`ProjectUser:ExportCredentials`** (`authorizeRestRoute` at `:158-161`; the permission is a standalone row in no standard group, `packages/@grantjs/constants/src/permissions/permissions.ts:1243-1248`, seeded instance-wide). The authorized-scope guard refuses an input scope that differs from the request's authorized scope (`apps/api/src/lib/authorization/operation-scope.ts:51-64`, applied by `graphql-guard.ts:99` and `rest-guard.ts:56`).
- **Handler** `UserHandler.exportProjectUserCredentials` (`apps/api/src/handlers/users.handler.ts:583-603`): project scope only (`OrganizationProject` / `AccountProject`, `isProjectTenant` `:339-341`), `kinds` defaults to `[PASSWORD]` and must not be empty (`:605-612`), `userIds` non-empty UUIDs within one page; one transaction: **every** id must be a member (any non-member is `NotFoundError`, nothing read or audited), then the service.
- **Service** `ProjectUserCredentialExportService.exportCredentials` (`apps/api/src/services/project-user-credential-exports.service.ts:29-61`): reads hashes through the one dedicated repository read `findHashesForExport` (port `IProjectCredentialRepository`, `packages/@grantjs/core/src/ports/repositories/credential.repository.port.ts`), writes **exactly one** audit row in the same transaction through `IExportAuditLogger.logExport` (`apps/api/src/lib/audit/drizzle-audit-logger.ts:125-130`: `action = 'export'`, no entity id, `performedBy` the caller, metadata `{ projectId, userCount, credentialCount, kinds }`; a failed write **throws**, so no audit row means no export), and returns `{ users: [{ userId, password: { algorithm: 'bcrypt', hash } | null }] }` in request order. The audit table's `metadata` column is `varchar(1000)` (`packages/@grantjs/database/src/schemas/project-user-credentials.schema.ts:93`), so a list of key ids does not fit in it (finding 5).
- **Kinds.** `enum CredentialKind { PASSWORD }` (`packages/@grantjs/schema/src/schema/project-users/types/credential-kind.graphql:5-8`), designed so that "a later credential type is a **new kind and not a second export**" (ADR 0011 § 4, `decisions/0011-password-as-a-scoped-credential.md:669-673`). This story is that later kind.
- **Fingerprint check.** `User.passwordCredential { source, updatedAt, fingerprint }` (ADR 0011 § 5, `:698-718`): `credentialFingerprint(hash)` is the lowercase hex SHA-256 of the **stored bcrypt hash string**, computed on read, never stored, never derived from the password (`apps/api/src/lib/credential-fingerprint.lib.ts`); resolved in the request's project scope and only for a caller holding `ProjectUser:ExportCredentials`, `null` otherwise (`users.handler.ts:640-679`, `apps/api/src/graphql/resolvers/users/fields/password-credential.resolver.ts`). It is GraphQL-only; the REST user shape has no such field. Its tests: `apps/api/tests/unit/services/project-user-credential-exports.service.test.ts`, `apps/api/tests/e2e/scenarios/operator-set-password-export.e2e.test.ts` (grants the permission to a Dev role's group through the database and exports with a session and with an API key).
- **What is missing.** The export knows one kind and reads one table. Nothing in it names an API key, and the export audit logger cannot name an entity.

### How API-key secrets are generated and hashed today; the `api_keys` columns

- **Generation.** `ApiKeyService.generateApiKey` (`apps/api/src/services/api-keys.service.ts:214-219`): `clientId` a UUID, `clientSecret` **32 random bytes as unpadded base64url (43 characters)**; `rotateApiKey` repeats the same expression inline (`:730`). `createApiKey` (`:304-357`) hashes with `hashSecret` (bcrypt, `config.token.bcryptRounds`, `apps/api/src/lib/token.lib.ts:42-44`), inserts, audits `CREATE_API_KEY`, publishes `api_key.created`, and returns the plaintext once in `CreateApiKeyResult.clientSecret`; `rotateApiKey` (`:710-778`) does the same with `ROTATE_API_KEY` and `api_key.rotated`. The CDM paths take the importer's secret (BYOK, `clientSecretSchema` min 32 characters, `apps/api/src/services/api-keys.schemas.ts:19`) or a pre-computed hash: `createApiKeyForCdmImport` (`:359-427`), `createApiKeysForCdmImport` (`:429-`), `rotateApiKeysForCdmImport` (`:533-586`, writes the hash only, audit `ROTATE_API_KEY_CDM`, no event).
- **Verification.** `exchangeApiKeyForToken` (`:605-690`) reads the hash by the dedicated `getClientSecretHash` (`apps/api/src/repositories/api-keys.repository.ts:257-266`) and `verifySecret` = `bcrypt.compareSync` (`token.lib.ts:55-57`). **bcrypt uses only the first 72 bytes of its input** (`bcrypt@6.0.0`, README line 41; verified in this worktree: a hash of an 88-character string compares `true` against the same string with its last 16 characters changed). This already applies to imported BYOK secrets, which may be longer than 72 bytes (finding 1).
- **Columns.** `api_keys` (`packages/@grantjs/database/src/schemas/api-keys.schema.ts`): `id`, `client_id varchar(255)`, `client_secret_hash varchar(255) not null`, `name`, `description`, `expires_at`, `last_used_at`, `is_revoked`, `revoked_at`, `revoked_by`, `created_by`, `created_at`, `updated_at`, `deleted_at`; no scope column, no project column: a key's project and owner live in the pivot `project_user_api_keys (api_key_id, project_id, user_id, metadata, deleted_at)` under RLS (`project-user-api-keys.schema.ts`). The repository returns whole rows as `ApiKey` (`toApiKey`, `api-keys.repository.ts:65`), so a column added to `api_keys` travels with every read until the output schema strips it; the CDM export selects named columns (`apps/api/src/repositories/project-export.repository.ts:496-515`). The newest migration is `0093_cdm_import_tombstones.sql` (journal idx 93); **no open pull request exists in the repository and no local branch carries an unmerged migration** (checked 2026-10-30), so the story's migrations are `0094` and `0095` and the sequencing condition of the request ("after the CDM replace-unchanged-keys stack", #625) is met on `42afcf0b`.
- **Fingerprints that exist.** For CDM-imported keys only, `fingerprintCdmApiKeySecret` is an HMAC-SHA256 of the plaintext under `CDM_API_KEY_FINGERPRINT_HMAC_SECRET`, stored in the pivot's `metadata.cdmImport.secretFingerprint` for replace classification and never exported (`apps/api/src/lib/cdm/cdm-api-key-fingerprint.lib.ts:46-48`, `docs/core-concepts/cdm-import-export.md:332-344`). Nothing exposes any fingerprint of a Grant-generated key.
- **What is missing.** No reversible copy, no format other than 43-character base64url, no fingerprint a receiver can read, and the plaintext is gone after the one response.

### Whether a per-project opt-in or settings mechanism exists to reuse

- `projects` has flat per-project columns and no settings object: `primary_color`, `show_help_panel` (`packages/@grantjs/database/src/schemas/projects.schema.ts`), surfaced as `Project.primaryColor` / `showHelpPanel` and set through `UpdateProjectInput` under `Project:Update` (`packages/@grantjs/schema/src/schema/projects/inputs/update-project.graphql`), audited by `ProjectService.updateProject` as one `UPDATE` row with old and new values on `project_audit_logs` (`apps/api/src/services/projects.service.ts:108-138`). `Project:Update` is held by the groups `ProjectOwner`, `ProjectAdmin`, `ProjectDev` (Organization Owner, Admin, **Dev**) and `AccountProjectOwner` (Personal Account Owner, Organization Account Owner) (`packages/@grantjs/constants/src/permissions/groups.ts:133-137,358-372`). The roles that manage API keys are the same three organization roles (`ApiKeyOwner` / `ApiKeyAdmin` / `ApiKeyDev` hold `ApiKey:Create`, `Delete`, `Revoke`, `groups.ts:536-550`); there is no `ApiKey:Rotate` action (rotate is gated by `ApiKey:Revoke`, `apps/api/src/rest/routes/api-keys.routes.ts:105-111`).
- The precedent for an action a Dev must not hold is `ProjectUser:SetPassword`: an ordinary action placed in the Owner and Admin groups only (ADR 0011 § 3, `rbac.md:258`).
- **What is missing.** No flag means "this project keeps exportable API-key secrets", and no path deletes anything when a flag turns off.

### How `api_key.rotated` is published, and what v1.21.0 gives the receiver

- `rotateApiKey` publishes `{ type: 'api_key.rotated', aggregate: { kind: 'apiKey', id }, subjectUserId, data: { before, after }, projectIds }` (`api-keys.service.ts:757-766`); `before` / `after` are `{ id, clientId, name, description, expiresAt }`, never the secret or the hash, and the external envelope carries only identity keys (`docs/core-concepts/events-webhooks-notifications.md:177`: `id`, `name`). Webhook redaction blanks any key matching `/secret/i`, `/clientsecret/i`, `/password/i` (`apps/api/src/lib/webhooks/webhook-redaction.lib.ts:17-22`); omission, not redaction, is the control used by `project.user_password_set`.
- **Since v1.21.0** `api_key.created`, `api_key.rotated` and `api_key.revoked` name the key's owning project user as `subjectUserId` (the envelope's `grantsubjectuser`) when the key has exactly one owner in `project_user_api_keys`, and reach the owning project's subscriptions (`:82`). So a receiver subscribed to the project learns **which key** (`aggregate.id`) of **which user** (`grantsubjectuser`) was created or rotated, and can ask for that user's credentials by the user id it already mirrors. The sentinel test `apps/api/tests/unit/services/api-keys.service.secret-events.test.ts` hoists `generateRandomBytes` to return a known value and asserts it reaches no event, envelope, audit value or log line; this story extends it.
- **What a receiver cannot do today:** read a project user's keys. `apiKeys(scope)` lists the keys of the named scope, and the authorized-scope guard requires every named scope to equal the request's authorized scope in tenant **and** id (`operation-scope.ts:51-64`); an API key authorized in an `OrganizationProject` scope cannot name an `OrganizationProjectUser` or `ProjectUser` scope, so it can list account and organization-project keys only. No query returns `ProjectUserApiKey` (`packages/@grantjs/schema/src/schema/project-user-api-keys/` has inputs and the type, no query), and `User` has no API-key field. This shapes where the fingerprint goes (finding 3).

### Findings that shape the criteria

These came from reading the code, not from the request, and each changes a criterion.

1. **Secret format: the receiver-compatible form already works in Grant, and bcrypt truncates it.** The receiver's system stores the plaintext as padded standard base64 of 64 random bytes (88 characters) and verifies `sha256(base64decode(secret) ‖ Date header)` against the decoded client-supplied value, so the only constraint on Grant's side is that the secret be decodable by a **standard** base64 decoder. Grant's 43-character unpadded base64url form is not: a standard decoder rejects `-`, `_` and the missing padding, so under option (2) the receiver must re-encode the same 32 bytes as 44-character padded standard base64, and the partner then holds a string that Grant's own `/auth/token` does **not** accept (bcrypt verifies the 43-character string). Two strings for one key. Under option (1) one 88-character string works in both systems, and nothing in Grant rejects it: `clientSecretSchema` is `min(32)`, the exchange verifies whatever string was hashed, and CDM imports already bcrypt importer secrets of this very form (`project-user-api-key.cdm-entity.ts:389`, `hashSecretAsync`), so the 88-character form has been exchanged in Grant since BYOK import exists. The cost is bcrypt's 72-byte input limit: the hash covers the first 72 characters (54 bytes, 432 bits of entropy), and the last 16 characters are not verified; this is already true of every imported BYOK secret longer than 72 bytes, so the story states it in the docs and does **not** change hashing (pre-hashing before bcrypt would change every BYOK verification). Criterion S2.2 and Gate 1 question 1. The signing proof against the receiver's system is the receiver's procedure, outside Grant (non-goal); the in-Grant half (the exported string exchanges for a token) is an e2e assertion, S3.6.
2. **"The same primitive" is the lib, not the key.** `project-oauth-connection.lib.ts` is sound but single-purpose; copying it would add a second code path for one behaviour. The story extracts the purpose salt into a parameter (one generic `sealSecret` / `unsealSecret` pair; the two OAuth functions become one-line wrappers with their purpose constant, output format unchanged, existing tests prove it) and binds the new purpose to a **dedicated key**, as ADR 0008 did for OAuth against MFA. Criterion S2.1, Gate 1 question 6.
3. **"A fingerprint on the key read" has no reachable key read for the receiver.** Under the authorized-scope guard an org-project API key cannot list a project user's keys (above). The reachable read in a project scope is `users(scope:, ids:)`, where D21 already put `User.passwordCredential`. The fingerprint therefore goes on **`User.apiKeyCredentials`**, a list over the member's live project-user keys, resolved in the request's project scope and gated by `ProjectUser:ExportCredentials` exactly like `passwordCredential`; a receiver reads both fingerprints in one query. A field on `ApiKey` would be reachable by session users only. Criterion S2.4, Gate 1 question 4.
4. **Fingerprint derivation: of the hash, not the plaintext.** `credentialFingerprint(client_secret_hash)` works for **every** key (opted in or not, imported or not), needs no new column, changes on create, rotate and CDM rotate, and is never derived from the plaintext, so a low-entropy importer-chosen BYOK secret cannot be guessed offline from it; a SHA-256 of the plaintext would be exactly such an oracle for imported keys. It reuses the D21 lib unchanged. Criterion S2.4, Gate 1 question 4.
5. **The audit row cannot name the key ids in the existing export row.** `project_user_credential_audit_logs.metadata` is `varchar(1000)`; one page of key ids is several thousand characters. The export therefore keeps its one summary row (counts and kinds, `credentialCount` counting secrets returned too) and adds **one row per exported secret on `api_key_audit_logs`** (`api_key_id` the key, `action = 'export'`, `performedBy` the caller, metadata `{ projectId, userId }`), all in the export transaction, through the same throwing export logger given an entity id. Criterion S3.3.
6. **"Refused for a key without a copy" becomes "listed with `secret: null`".** The export is keyed by user, and the D21 shape lists a member without a credential as `password: null` rather than failing. A key without a copy (created before the opt-in, imported, or rotated by a CDM replace) is listed with its id, `clientId` and fingerprint and `secret: null`, so the receiver can tell "no key" from "no copy" without a second call. The whole-call refusal stays for a non-member. Criterion S3.1, Gate 1 question 7.
7. **A copy must never outlive the hash it matches.** `rotateApiKeysForCdmImport` changes the hash without knowing a plaintext the receiver needs (the importing system holds it), and revoke and delete end the key's life. Any path that changes or retires the hash removes the copy; the invariant "a copy, when present, decrypts to the secret the current hash verifies" is tested. Criterion S2.3.
8. **The previous secret is not needed after a rotation.** The receiver wrote the previous secret into its system itself, so it already holds it and can move it into that system's grace slot without Grant; Grant's own exchange never accepts a previous secret; and keeping it doubles the reversible material at rest. If a receiver misses a rotation, the fingerprint shows the change and the export returns the current secret; the intermediate one was never valid in the receiver's system. Criterion S2.3, Gate 1 question 3.

Project scope only (`OrganizationProject` / `AccountProject`), the scope the transport authorized (guard). Same value is a no-op (no write, no audit row). ### S2 — the encrypted copy, its format, and the fingerprint (slice 2)

- [ ] **S2.1 The primitive, generalised, and a dedicated key.** `apps/api/src/lib/sealed-secret.lib.ts` exports `sealSecret(plaintext, keyMaterial, purpose)` and `unsealSecret({ encryptedSecret, secretIv, secretTag }, keyMaterial, purpose)` with the body of `project-oauth-connection.lib.ts` (AES-256-GCM, scrypt with the same parameters, the purpose string as the KDF salt). `encryptProjectOAuthConnectionSecret` / `decryptProjectOAuthConnectionSecret` become one-line wrappers with their existing purpose constant: no caller changes, same output, the existing OAuth unit tests and `project-oauth-byo.e2e.test.ts` pass unchanged. The new purpose is `grant-platform:api-key-exportable-secret-encryption:v1`; the key is **`API_KEY_EXPORTABLE_SECRET_ENCRYPTION_KEY`**, declared everywhere `PROJECT_OAUTH_CONNECTION_ENCRYPTION_KEY` is (the 20 files listed in "already true", `apps/config` included), resolved at point of use through `ISecretResolver`. If Gate 1 question 6 picks reuse, the new purpose keeps its own salt and reads the OAuth variable.
- [ ] **S2.2 Copy at create and rotate, in the receiver-compatible form.** New table `api_key_exportable_secrets` (`id`, `api_key_id` → `api_keys(id)` on delete cascade, **unique**, `project_id` → `projects(id)` on delete cascade, `encrypted_secret varchar(4000)`, `secret_iv varchar(255)`, `secret_tag varchar(255)`, `created_at`, `updated_at`; the two tenant RLS policies of `project_user_api_keys`), migration `0095_api_key_exportable_secrets.sql`. In `ApiKeyService.createApiKey` when `owner` is given, and in `rotateApiKey` when `resolveOwnerSubject` yields exactly one owner, the service reads the owning project's flag; when it is on, the secret is **64 random bytes as padded standard base64 (88 characters)** instead of 32 bytes base64url, is bcrypt-hashed as today, and is sealed and written (insert, or replace in place on rotate) in the same transaction; when the key is missing, `ConfigurationError` and no key is issued (fail closed; the project opted in). Keys of projects not opted in, account and organization-project keys, and every CDM path are **unchanged** (no copy, Grant's form). The docs state bcrypt's 72-byte rule (finding 1). If Gate 1 question 1 picks option (2), only the format line changes: the copy is the 43-character string and the docs tell the receiver to re-encode.
- [ ] **S2.3 The copy never outlives its hash.** `revokeApiKey`, `deleteApiKey` (soft; hard cascades by FK), `deleteApiKeysForCdmImport` (cascade) and `rotateApiKeysForCdmImport` delete the key's copy in the same transaction; disabling the flag (S1.4) deletes the project's copies and reports the count. No previous secret is kept (finding 8). A unit test states the invariant: after any of these, a copy present for a key decrypts to a string the key's current hash verifies.
- [ ] **S2.4 The fingerprint read.** `User.apiKeyCredentials: [ProjectUserApiKeyCredential!]` with `ProjectUserApiKeyCredential { apiKeyId: ID!, clientId: String!, fingerprint: String!, exportable: Boolean!, updatedAt: Date! }`: the member's live, unrevoked project-user keys in the request's project scope, `fingerprint` = `credentialFingerprint(client_secret_hash)` (finding 4), `exportable` = a copy exists, `updatedAt` = `api_keys.updated_at`. Resolved like `passwordCredential` (`users.handler.ts:640-679`): `null` outside `OrganizationProject` / `AccountProject`, `null` unless the actor holds `ProjectUser:ExportCredentials` (a denial is `null`, never an error), `[]` for a member with no key. One dedicated repository read returning `apiKeyId`, `clientId`, `clientSecretHash`, `updatedAt` and `hasCopy` for the user's keys (a join on the pivot and a left join on the copy table; the hash leaves the repository to the service only, which returns the digest). ## Decisions for Gate 1

Each question has a recommended answer; the criteria above are written for it.

1. **Secret format for opted-in keys.** (1) 64 random bytes, padded standard base64, 88 characters: one string works in Grant's exchange and in the receiver's decoder, as imported BYOK secrets of that form already do; bcrypt covers the first 72 characters (finding 1, stated in docs). **Recommended: (1).** Alternative (2): keep Grant's 43-character base64url form and have the receiver re-encode; a standard decoder rejects it as-is, and the re-encoded 44-character string is not accepted by Grant's exchange, so the partner holds two strings for one key.
2. **Where the opt-in lives and who flips it.** A `projects` column, a dedicated mutation and REST route, gated by a new `Project:SetExportableApiKeySecrets` in the Owner and Admin project groups and the account-project owner group, not Dev (the `SetPassword` precedent). **Recommended.** Alternatives: a field on `UpdateProjectInput` under `Project:Update` (no new route or permission, but Dev may flip it and the copy deletion becomes a side effect of a generic update); a per-key flag (rejected by the request's own decision).
3. **Previous secret after a rotation.** Not kept; one copy per key, replaced in place (finding 8). **Recommended.** Alternative: keep one superseded copy and return it as `previousSecret` (a second row or triple per key; more reversible material; the receiver does not need it).
4. **Fingerprint derivation and surface.** `credentialFingerprint(client_secret_hash)` (SHA-256 of the stored bcrypt hash; never of the plaintext), on **`User.apiKeyCredentials`** in the request's project scope, gated like `passwordCredential` (findings 3 and 4). **Recommended.** Alternatives: SHA-256 of the plaintext stored at copy time (lets a receiver verify the secret it holds, but is a guessing oracle for weak imported secrets and exists only for opted-in keys); a field on `ApiKey` (unreachable for the receiver's key under the authorized-scope guard).

   **Decided at Gate 1 (Alejandro, 2026-10-30), differently from the recommendation above:** the fingerprint is the lowercase hex **SHA-256 of the secret string as issued** (the 43- or 88-character text the client receives), never of the bcrypt hash. Reason: a receiver that stores the plaintext secret compares its own `sha256(stored secret)` with Grant's fingerprint to detect a create or rotate and to verify an export; a hash-of-hash cannot be compared or verified without the bcrypt hash. Consequences for S2: Grant computes the fingerprint at create and rotate for **every** project-user key from this release on (opted in or not; the plaintext is in hand only then), stores it in a new nullable column `api_keys.client_secret_fingerprint` (the stack plan names it), and `ProjectUserApiKeyCredential.fingerprint` becomes `String` (nullable): `null` for a key created before this release and not rotated since. The export (S3) returns the same fingerprint beside the secret so the receiver can verify the pair. A 32- or 64-byte random secret makes the unsalted hash safe against guessing; the ADR states this.

5. **Permission for exporting a key secret.** The same `ProjectUser:ExportCredentials`: ADR 0011 built `kinds` so a later credential type is a new kind, not a second export, and the holder is the same machine. **Recommended.** Alternative: a distinct standalone `ApiKey:ExportSecret` (finer, two standalone grants for one mirror, two gates on one route).
6. **Encryption key.** A dedicated `API_KEY_EXPORTABLE_SECRET_ENCRYPTION_KEY` with its own purpose salt, through the generalised lib (finding 2), following ADR 0008's blast-radius reasoning. **Recommended.** Alternative: reuse `PROJECT_OAUTH_CONNECTION_ENCRYPTION_KEY` with a distinct purpose salt (one variable fewer across 20 files; rotating it then re-wraps two kinds of secret).
7. **A key without a copy in the export.** Listed with `secret: null` beside its id, `clientId` and fingerprint (finding 6). **Recommended.** Alternative: the whole call fails with `NotFoundError` ("refused", as the request words it), which makes the receiver filter by `exportable` first.
8. **Copies on CDM paths.** Never written by an import; a CDM rotate of an opted-in key deletes the existing copy (finding 7). **Recommended.** Alternative: an import of a BYOK secret into an opted-in project also writes a copy (the importing system already holds the plaintext; more copies for no reader).
9. **Where the decision is recorded.** A new ADR 0013 plus a one-sentence pointer in 0011 § 4; `decisions/README.md` forbids editing an accepted decision and 0011 is about passwords. **Recommended.** Alternative: a second amendment section in 0011 (the 2026-10-29 precedent), which buries reversible storage inside a password record.
10. **Review bars.** Security-full on all three slices, Security blocking, independent reviewer before each gate 3. **Recommended as stated.**
11. **Release.** Minor, **v1.22.0**: two migrations, a new permission, a new route, a new enum member and new fields. **Recommended: minor.** Alternative: none sensible (a route and a permission are not a patch).
12. **Slice count.** Three (opt-in; copy, format and fingerprint; export kind), each one concern and each inert on its own for the receiver until the next lands; the stack plan gives the order and the two-slice collapse as the alternative. **Recommended: three.**
