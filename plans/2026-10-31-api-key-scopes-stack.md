## Ordered slices (PRs)

Init `gh stack` with **slice 1 only**; `gh stack add` the next branch immediately before writing it.

**Order and the reason.** Slice 1 (model and attenuation) is the hardening of the role check and the contract every other slice depends on: it makes the role nullable, adds the permissions table, and replaces the hierarchy check with containment for both tenants and both grant kinds, while **exposing nothing new** (no schema, REST or OpenAPI change), so it is reviewable as "who may bind what to a key" and lands whatever happens above it. Slice 2 (resolution and surface) needs slice 1's table, service and constants: it makes a scope key authorize by its permissions, exposes `permissionIds`, `ApiKey.permissions`, the cohort query and the edit mutation, and documents them. Slice 3 (web) needs slice 2's operations and types (`@grantjs/schema` codegen). Slice 4 (ADR and the mirror example) records the decisions after the code they describe exists on the trunk; it is docs-only and may be drafted while slice 3 is in review. The order is also Grant's layer order within slices 1 and 2 (constants → database → core ports → repository → service → handler → schema → resolvers and routes → web).

**Overlapping files found** (the stacking order resolves every overlap in one direction): slices 1 and 2 both edit `apps/api/src/handlers/api-keys.handler.ts` (1: call the attenuation service in both tenants' create, revoke, rotate and delete, accept `permissionIds` internally; 2: pass the input field through, add `enrichApiKeysWithGrants`, the cohort and set handlers), `apps/api/src/services/grant.service.ts` (1: extract `collectPermissionIds`; 2: add the API-key path), `packages/@grantjs/core/src/ports/services/api-key.service.port.ts` (1: `IApiKeyAttenuationService`; 2: `attachableGrants` result type, `setPermissions`), `docs/core-concepts/api-keys.md` and `docs/architecture/rbac.md` (1: the rule and the new action; 2: the surface; 4: the mirror example and the ADR pointer). Slices 2 and 3 share nothing but generated code (`packages/@grantjs/schema/src/generated`, regenerated in each). Slice 4 touches `decisions/*`, `docs/core-concepts/api-keys.md` and `docs/architecture/rbac.md` only.

**Three-slice alternative (Gate 2 may pick it).** Fold slice 4 into slice 2 (the ADR and the mirror example land with the surface they describe). One PR fewer, and the ADR is reviewed by the same Security pass as the resolution change; at the price of a security-full PR that also carries ~300 lines of prose, and of writing the record before the web's conversion flow (which the ADR describes) exists on the trunk. Four is recommended because the ADR is the Architect's artifact and its review question ("is this the decision we made") is different from slice 2's ("is this resolution path correct"). **Not recommended:** merging slices 1 and 2; slice 1 alone is the hardening and must stay reviewable on its own (and releasable alone under Gate 1 question 14).

**Fan-out.** Slices 1 → 2 → 3 are sequential by dependency: one writer at a time in this worktree. Slice 4 may be **drafted in parallel with slice 3's review** by the Architect in a second worktree (`/Users/aleheredia/workspace/worktrees/grant-platform-feat-api-key-scopes-adr`, docs-only files, no conflict with slice 3's files), then pushed and its worktree removed before `gh stack` adopts it. Within a slice: Verifier after the author; Security reads slices 1 and 2 as a reviewer who is not the author (agentic-sdlc § Fan-out), scheduled before that slice's gate 3, not folded into gate 4; QA drives slice 1's and slice 2's e2e and slice 3's component tests.

**Size and the fallback seams.** Estimates: slice 1 about 450 lines of source (constants, two schema edits and a new one, migration, port, repository, service, handler changes, service-port cleanup) and 650 of tests and docs; slice 2 about 420 and 650; slice 3 about 700 (two pages × two trees, viewer, five cards, the table, hooks, store, operations, i18n in two locales) and 250 of tests; slice 4 about 350 lines of docs. If an implemented diff is too large to review at once, the executor does **not** hand over a mega-diff: it stops and reports the split. Slice 1 splits at `feat/api-key-scopes-model-db` (constants, schemas, migration, repository and port; inert: nothing reads the table) below `feat/api-key-scopes-model-check` (the service, handler wiring, removal of the old checks, tests); the lower half alone changes no behaviour. ## Stack setup

Root the stack on the story trunk, never the default branch, or the slices target `main` and skip gate 4:

```sh
# Trunk — exists locally with the two plan files. After Gate 1: push it.
cd /Users/aleheredia/workspace/worktrees/grant-platform-feat-api-key-scopes
sh .husky/pre-push && git -c core.hooksPath=.husky push -u origin feat/api-key-scopes

# After Gate 2: init with the FIRST slice branch only.
gh stack init --base feat/api-key-scopes feat/api-key-scopes-model

# After each slice: commit, then BOTH of these, every time.
gh stack submit --auto                                   # --auto: no interactive editor
gh stack link --base feat/api-key-scopes <pr> <pr> …     # bottom to top; creates/grows the stack ON GitHub

# Before the NEXT slice — creates the branch on the current tip and pushes nothing:
gh stack add feat/api-key-scopes-api
# … work, commit, submit, link; then
gh stack add feat/api-key-scopes-web
# … then
gh stack add feat/api-key-scopes-adr

# After any merge, rebase or amend below a branch:
gh stack sync
```

Check positions before writing each slice, not after:

```sh
git for-each-ref --format='%(refname:short) %(objectname:short)' refs/heads
gh pr view <bottom-pr> --json baseRefName   # must be feat/api-key-scopes, never main
```

`gh stack` cannot switch to a branch that is checked out in another worktree, so a slice written in a second worktree (slice 4) is pushed and its worktree removed before `gh stack` is asked to adopt or restack it. See [Agentic SDLC § GitHub stacking](../docs/contributing/agentic-sdlc.md#github-stacking). **`--base` is not optional on `link`.** `gh stack submit --auto` opens PRs as **drafts**; mark ready with `gh pr ready <pr>` for gate 3. Only the orchestrator runs `gh stack`; executors open plain PRs against the slice below.

**Hooks.** `git config core.hooksPath` is unset in this worktree (verified 2026-10-31), so: `git -c core.hooksPath=.husky commit` on every commit (lint-staged runs prettier); `sh .husky/pre-push` by hand before every push (`.husky/pre-commit` and `.husky/pre-push` are mode 755 at `23869429`, so `git -c core.hooksPath=.husky push` runs it too; run it by hand regardless, it is the full chain: `format:check`, `lint`, the seven `dead-code:*` targets, `codegen:check`, `type-check`, `build`, `synth:check`, `CI=1 pnpm test`, `secret-scan:protect`); `pnpm release:check` by hand whenever a changeset is in the diff (a changeset naming an ignored package such as `@grantjs/core`, `@grantjs/database` or `@grantjs/constants` passes locally and fails CI, `.changeset/config.json` `ignore`). Never `--no-verify`, never `HUSKY=0`. Migrations: `pnpm --filter @grantjs/database db:generate`, rename the file (`0096_api_key_permissions.sql`), `db:migrate` against the local stack; the e2e stack picks it up through `scripts/e2e.sh`. **Dead code:** slice 1 removes three service methods and their port declarations (`validateOrganizationProjectApiKeyRolePermission`, `validateCanManageOrganizationProjectApiKey`, `filterApiKeysByManageable`); `dead-code:api` and `dead-code:core` must stay clean, so nothing new may be exported unused in slice 1 (the cohort computation is exercised by slice 1's unit tests and exposed in slice 2). **Codegen:** slices 2 and 3 run `pnpm --filter @grantjs/schema generate` and commit `src/generated`; `codegen:check` diffs it. **`boot-parity`** is unchanged on slices 1, 3 and 4 and changes by exactly two routes on slice 2 (`apps/api/tests/e2e/__snapshots__/boot-parity.e2e.test.ts.snap`, beside `:86-88`). **Security wording:** slice 1's changeset, PR title and body describe the change as a hardening and nothing more (brief risk flags, SECURITY.md); the e2e of S1.5 is named `api-key-attenuation.e2e.test.ts`. Agents never self-merge. Alejandro merges.
