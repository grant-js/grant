## Objective

A project API key (`accountProject` or `organizationProject` scope) can carry an explicit set of permissions, its **scopes**, instead of a parent-tenant role, the way fine-grained tokens do on other platforms. Whatever a key carries, role or scopes, must be **covered by what its creator can do in the key's scope**: attenuation replaces today's role-level hierarchy check and hardens it for every role a tenant may carry. A small set of **machine-only permissions**, starting with `ProjectUser:ExportCredentials`, may be attached by a creator who does not hold them, under a declared rule. The dashboard gets a dedicated create view with a scope picker, a key detail view with a scopes card, and (recommended) an edit path for the scopes of an existing key. Project-user API keys are untouched: they stay the credentials of their project user.

## What is already true, and what is missing

Read from `origin/main` at `23869429`.

### The two pivots and the role they carry

- `organization_project_api_keys (id, organization_id, project_id, api_key_id, organization_role_id NOT NULL → roles, created_at, updated_at, deleted_at)` with a partial unique index on `(organization_id, project_id, api_key_id)` and the organization/project RLS pair (`packages/@grantjs/database/src/schemas/organization-project-api-keys.schema.ts:18-64`). `account_project_api_keys` is its mirror with `account_id` and `account_role_id NOT NULL` (`account-project-api-keys.schema.ts:18-64`). Each has its own audit table (`*_api_key_audit_logs`, `varchar(1000)` value columns). `project_user_api_keys` has no role: a project-user key is the user (`project-user-api-keys.schema.ts:17-56`). `api_keys` itself has no tenant, role or permission column (`api-keys.schema.ts:6-35`).
- **GraphQL and REST.** `CreateApiKeyInput { name, description, expiresAt, scope!, roleId }`, `roleId` documented as "required when scope.tenant is accountProject or organizationProject: the parent-tenant role the key impersonates" (`packages/@grantjs/schema/src/schema/api-keys/inputs/create-api-key.graphql`); `ApiKey.role: Role` "null for user-scoped keys" (`types/api-key.graphql`). REST `POST /api/api-keys` body has the same optional `roleId` (`apps/api/src/rest/schemas/api-keys.schemas.ts:29-47`); OpenAPI says the role "must belong to the parent tenant … and defines the permissions the key has for that project only" (`apps/api/src/rest/openapi/api-keys.openapi.ts:186-189`). Five API-key routes are in `boot-parity` (`apps/api/tests/e2e/__snapshots__/boot-parity.e2e.test.ts.snap:5,29,86-88`: `GET`, `POST`, `POST /{id}/revoke`, `POST /{id}/rotate`, `DELETE /{id}`). The role shown on a listed key comes from the handler, which reads the pivot rows of the scope and joins roles (`apps/api/src/handlers/api-keys.handler.ts:73-118`); there is no field resolver on `ApiKey`.
- **Creation** (`api-keys.handler.ts:120-220`): project-user scopes create the key with an `owner` and the project-user pivot (`:127-152`); **`AccountProject`** resolves a missing `roleId` to the caller's account role (`accountProjectApiKeys.resolveAccountRoleIdForCurrentUser`, `:156-161`) and otherwise **validates nothing** about a supplied one before `addAccountProjectApiKey` (`:162-180`; the service only checks the role is one of the account's roles, `account-project-api-keys.service.ts:47-59,87`); **`OrganizationProject`** requires `roleId` (`:184-188`) and calls `validateOrganizationProjectApiKeyRolePermission` (`:190-194`) before `addOrganizationProjectApiKey` (`:203-211`), whose `ensureOrganizationHasRole` checks the role is in `organization_roles` (`organization-project-api-keys.service.ts:69-81,208-209`).
- **The role check** (`validateOrganizationProjectApiKeyRolePermission`, `organization-project-api-keys.service.ts:100-128`): reads the caller's organization membership role name and calls `canAssignRole(currentUserRoleName, targetRoleName)` (`packages/@grantjs/constants/src/permissions/roles.ts:67-76`), a comparison of the hierarchy levels of the **standard organization roles** (Owner 1, Admin 2, Dev 3, Viewer 4; `:40-51`) that was written for member role changes; it requires `targetLevel > currentLevel`, so an Owner may not create an Owner-role key today. The same function gates revoke, rotate and delete of an organization-project key through `validateCanManageOrganizationProjectApiKey` (`:130-172`, called from the handler at `:238,:256,:273` for `OrganizationProject`; the `AccountProject` branches run no manage check), and `filterApiKeysByManageable` (`:174-193`) treats a key with no role as manageable (`:191`) and is called from nowhere in `apps/api/src` (unused on the server; the web has the same rule at `apps/web/components/features/api-keys/api-key-actions.tsx:70-75`). `canAssignRole` is also used for members and invitations (`organization-members.service.ts:94,177`, `organization-invitations.service.ts:114`) and in the web (`members/*`, `api-keys/*`); those uses are not this story's.

### How a key principal is authorized today

- **Exchange.** `POST /auth/token` resolves the key through the pivot of the named scope (`ApiKeyService.findScopedApiKeysByClientId`, `apps/api/src/services/api-keys.service.ts:245-287`); for a project key the principal id is **the key's own id** (`userId: apiKeys[0]?.id`, `:266,:275`; `exchangeApiKeyForToken` `:705`), for a project-user key it is the user. `signToken` issues `sub = userId`, `jti = apiKeyId`, `type = ApiKey`, `scope` (`:161-189`); the claims become `GrantAuth { userId, tokenId, type, scope, grantedScopes? }` (`packages/@grantjs/core/src/types/index.ts:194-211`), where `grantedScopes` exists **only for project-app tokens** (`packages/@grantjs/core/src/core/grant.ts:94`).
- **Decision.** Every guard calls `handlers.auth.isAuthorized` (`graphql-guard.ts:141`, `rest-guard.ts`), which caches the result per `(userId, scope, resource, action, contextHash)` with a TTL equal to the token's remaining life (`apps/api/src/handlers/auth.handler.ts:931-975`; key format `cache-handler.ts:616-645`; project-app tokens add a `grantedScopes` signature) and otherwise asks `Grant.isAuthorized` (`core/grant.ts:175-215`): project-app tokens are **capped** to `grantedScopes` first (`:190-200`), then `PermissionChecker.check` (`core/permission-checker.ts:127-220`) asks `GrantService.getUserPermissions(userId, scope, resource, action, tokenType)` (`apps/api/src/services/grant.service.ts:124-160`), which unions **roles in scope → groups → permissions**, **roles → direct role permissions** (filtered to `project_role_permissions` when the scope has a project, `grant.repository.ts:519-556`), **direct user groups** and **direct user permissions**, then filters the ids by resource and action (`getPermissionsByIds`).
- **The role of a key principal** is read in `GrantRepository.getUserRoleIdsInScope` (`apps/api/src/repositories/grant.repository.ts:221-420`): for `AccountProject` and `OrganizationProject` the "project API key path" looks the principal id up in the pivot of the scope and returns the pivot's role (`:283-300`, `:373-390`), before the user paths. **Group permissions of that role are not project-filtered** (`getGroupIdsForRoles` / `getPermissionIdsForGroups`, `:483-517`). `getGrantedScopeSlugs` (`grant.service.ts:162-180`) is the project-app intersection ("which of these `resource:action` slugs does the user hold") and is the closest thing to a cohort computation today.
- **Caches.** `addApiKeyIdToScopeCache` / `removeApiKeyIdFromScopeCache` (`cache-handler.ts:537-543`) maintain the **scoped id set** used for listing (`cache.apiKeys`), not authorization. Authorization results live under `auth:result:{principalId}:…`; `invalidateAuthorizationResultsForUser(principalId)` drops them by prefix (`cache-handler.ts:663-671`; used after membership and user-permission changes, `users.handler.ts:490,915,1348,1384`, `organization-members.handler.ts:40`) and `invalidatePermissionsCacheForAllScopes(scope)` drops a tenant's (`:600-612`).
- **What is missing.** Nothing reads a permission set for a key: a pivot row with no role yields `[]` roles, the user paths find no `user_roles` for a key id, and the key has no permissions.

### Permissions, groups, the standalone list, and who may author roles

- Permission rows are instance-wide `(resource, action, condition)` rows seeded from the group templates, one row per `resource:action` (`packages/@grantjs/database/src/scripts/seed-permissions.ts:246-293`); `STANDALONE_PERMISSIONS` (`packages/@grantjs/constants/src/permissions/permissions.ts:1260-1276`) seeds rows that belong to **no group**; its only member is `ProjectUser:ExportCredentials`, placed in no standard group **by design** so that nobody, Owner and Admin included, holds it by default and an organization "grants it deliberately to the group of the role a mirror's API key carries" (ADR 0011 amendment § 3, `decisions/0011-password-as-a-scoped-credential.md:644-660`; `docs/architecture/rbac.md:262`). The catalogue is 17 resources (`resources.ts:33-51`) and about 72 distinct `resource:action` pairs.
- The API-key groups: `ApiKeyOwner`, `ApiKeyAdmin`, `ApiKeyDev` each hold `ApiKey:Create`, `Delete`, `Revoke` for Owner, Admin, Dev (`groups.ts:551-565`; the Dev template carries **no** condition, `permissions.ts:1142-1158`, although `rbac.md:214` says Dev may delete/revoke own keys only); `ApiKeyCommon` holds `Query`, `Exchange` for every organization role (`:259-263`); `AccountProjectApiKeyOwner` holds `Create`, `Update`, `Delete`, `Query`, `Revoke` for the two account-owner roles (`:208-218`). **`ApiKey:Update` is not an action of the `ApiKey` resource** (`resources.ts:145-152`: `Create`, `Delete`, `Query`, `Revoke`, `Exchange`), so the account group's `Update` has no row to seed and no organization group holds it.
- **Role authoring.** `createRole` (gated by `Role:Create`, `apps/api/src/graphql/resolvers/mutations.ts:175-180`) is where a role's groups and permissions are set (`apps/api/src/handlers/roles.handler.ts:104-160`). It is outside this story (non-goals); the check this story adds does not depend on how a role was authored, because it compares a key's **effective** permission set with its creator's, whatever the role contains.

### Findings that shape the criteria

These came from reading the code, not from the request, and each changes a criterion.

1. **API-key role assignment is hardened.** `canAssignRole` compares the hierarchy levels that only the standard organization roles carry (`roles.ts:40-51,67-76`) and was written for member role changes; a key's role may be any role of the tenant, so a level comparison is not the right predicate for keys. S1 replaces it, for keys, with containment: the key's effective permission set must be covered by its creator's, whatever the role's name or level and whether or not it has one; the same check guards revoke, rotate and delete; a regression test pins each refusal (S1.4, S1.5). The member and invitation uses of `canAssignRole` are unchanged. **Criteria S1.3–S1.5; Gate 1 question 3; risk flags.**
2. **The account-project branch gets the same check.** Today a supplied `roleId` is checked for tenant membership only (`api-keys.handler.ts:156-180`, `account-project-api-keys.service.ts:47-59,87`), and revoke, rotate and delete run no manage check for `AccountProject` (`api-keys.handler.ts:236,254,271`). S1 applies containment and the manage check to both tenants, so a supplied role or permission set is always compared to the caller's. **Criteria S1.3, S1.4, S1.6.**
3. **Keys without a role need a manageability rule.** `filterApiKeysByManageable` (`:191`, unused on the server) and the web's `canManageApiKey` (`api-key-actions.tsx:73`) treat a key with no role as manageable. Scope keys have no role, so the server-side predicate becomes the containment check, the unused method is removed, and the web derives manageability from the cohort query (finding 7). **Criteria S1.4, S3.7.**
4. **"The creator's effective permissions in the key's scope" has one existing computation, and it is per action.** `GrantService.getUserPermissions` collects the principal's permission ids and then filters by one `resource:action` (`grant.service.ts:124-160`); `getGrantedScopeSlugs` loops it per slug (`:162-180`). The containment check needs the **whole set**, so the id collection is extracted into one method (`collectPermissionIds(userId, scope, tokenType)`) that `getUserPermissions`, `getGrantedScopeSlugs` and the new check all use: one path, as AGENTS.md and the house rule require. The comparand is evaluated in the **key's project scope** (`OrganizationProject` / `AccountProject`) with the creator's **actual token type**, which makes attenuation transitive (a key creating a key is bound by its own set) and lets the key's own set be computed by the same code (a role key's set = that role's groups and project-filtered direct permissions, exactly what the key would resolve to). **Criterion S1.3; Gate 1 question 2.**
5. **Containment makes `ProjectUser:ExportCredentials` unattachable unless a rule says otherwise.** No standard group holds it (above), so no creator's set contains it. The template-level rule recommended here is **permission-gated, not role-gated**: a standalone permission may declare `attachableByHoldersOf: { resource, action }`, and a creator who holds that gate permission in the key's scope may attach the machine-only permission without holding it. For the export the gate is `ProjectUser:SetPassword`, held by `ProjectUserOwner` (Organization Owner, Personal Account Owner, Organization Account Owner) and `ProjectUserAdmin` (Organization Admin) and no Dev, Viewer or common group (`groups.ts:614-627`), which is "Owner and Admin may attach it" without naming roles, covers account projects, and stays inside the permission model attenuation is built on. The flag describes attachability only; it does **not** deny the permission to sessions (Gate 1 question 5). **Criterion S1.3; Gate 1 question 4.**
6. **Editing needs an action that does not exist and a cache call that does.** `ApiKey:Update` is not declared on the resource (`resources.ts:145-152`), so editable scopes add it to the resource and to `ApiKeyOwner`, `ApiKeyAdmin`, `ApiKeyDev` (the account group already lists it, `groups.ts:208-218`, so its row starts being seeded). A scope change must drop the key's cached decisions: the principal id of a project key is the key id, so `invalidateAuthorizationResultsForUser(apiKeyId)` (`cache-handler.ts:663-671`) is exactly the existing call. Audit value columns are `varchar(1000)` (`api-keys.schema.ts:50-71`), and 72 permission ids do not fit, so the audit is **one row per added or removed permission** (the pivot-audit pattern of `assignRolePermission`), not one row with the list. **Criteria S2.4–S2.6; Gate 1 question 6.**
7. **The dialog cannot compute attenuation client-side, and neither can the actions menu.** `canAssignRole` in the web (`api-key-create-dialog.tsx:145`, `api-key-actions.tsx:74`) reads role names; containment needs the creator's permission set and each role's effective set, which only the server has. So the cohort query returns **both** the attachable permissions (flagged machine-only) **and** the attachable roles of the parent tenant, and the web derives "may create with" and "may manage" from it; `canAssignRole` leaves the API-key components (the member components keep it). **Criteria S2.3, S3.3, S3.7; Gate 1 question 9.**
8. **The picker is the existing attach table, extended with grouping; grouping replaces paging as the navigation.** The catalogue is 17 resources and about 72 pairs; the dashboard's attach components (above) are paginated checkbox tables, where a selection spread over pages is easy to get wrong, and none groups by resource. Building a bespoke picker would add a second component for one behaviour, so the scope picker is **`ProjectAppCreateScopes` generalised**: the same card, toolbar, checkbox column and footer, with the data source swapped for the cohort of S2.3 (permission rows, not slugs) and two documented extensions: **group header rows per resource** carrying an "all actions" checkbox (tri-state), and a page size that holds the whole catalogue, so the footer `Pagination`, which these components already render only when `totalPages > 1`, does not appear for today's catalogue and still works if one outgrows a page. The key **detail** view reuses `ProjectAppScopes` the same way (the card-with-table-and-pagination, edit in place). **Criteria S3.3–S3.6.**
9. **Nothing in the CDM touches project keys** (above), so no import/export, replace or tombstone path changes, and the receiver's own key is outside the data it mirrors. The mirror example in `api-keys.md` is therefore a **documentation** of the permission set the receiver's calls need, derived from the route guards (criterion S4.2), not a CDM change.

## Acceptance criteria

Slice numbering follows the stack plan: S1 model and attenuation (no surface), S2 authorization and API surface, S3 web, S4 ADR and the mirror example.

### S1 — data model, attenuation, the hardened check (slice 1, no surface change)

- [ ] **S1.1 Nullable role, one permissions pivot.** `organization_project_api_keys.organization_role_id` and `account_project_api_keys.account_role_id` become **nullable** (Drizzle `.notNull()` removed; the FKs stay). New table `api_key_permissions` (Drizzle `apiKeyPermissions`): `id`, `api_key_id` → `api_keys(id)` on delete cascade, `permission_id` → `permissions(id)` on delete cascade, `project_id` → `projects(id)` on delete cascade (for the project RLS pair of `api_key_exportable_secrets`, `0095`), `created_at`, `deleted_at`; partial unique index on `(api_key_id, permission_id)` where `deleted_at IS NULL`; indexes on `api_key_id`, `permission_id`, `project_id`. Migration `0096_api_key_permissions.sql` (generated by `pnpm --filter @grantjs/database db:generate`, renamed). Existing rows keep their role; **no backfill**. The invariant "a project key has exactly one of a role or a non-empty permission set" is enforced in the service (S1.3), not by a database constraint (it spans two tables), and unit-tested.
- [ ] **S1.2 Constants.** `ResourceAction.Update` added to the `ApiKey` resource (`resources.ts`) and to the `ApiKeyOwner`, `ApiKeyAdmin`, `ApiKeyDev` group templates (`groups.ts`, `permissions.ts`), so the row seeds and the account group's existing `Update` has a row; `rbac.md` and `resources.md` rows updated. `StandalonePermission` gains `attachableByHoldersOf?: { resource: ResourceSlug; action: ResourceAction }`; `ProjectUser:ExportCredentials` declares `{ ProjectUser, SetPassword }`; `MACHINE_ONLY_PERMISSIONS` (the standalone entries with the field) and `machineOnlyGate(resource, action)` are exported. If Gate 1 question 4 picks the role list, the field is `attachableBy: readonly RoleKey[]` and the check compares the creator's role instead.
- [ ] **S1.3 One attenuation check, both tenants, both kinds.** New `ApiKeyAttenuationService` (port `IApiKeyAttenuationService` in `@grantjs/core` ports/services, wired in `createServices`) with: `assertAttachable({ scope, roleId | permissionIds }, tx)` — the creator's **effective permission ids in the key's project scope** (`collectPermissionIds`, finding 4, the creator's own token type) ∪ the machine-only ids whose gate the creator holds must contain the requested set, where the requested set is the given `permissionIds` (each must exist, be live, and carry no condition the creator's matching row does not have; the match is by **row id**) or, for a role, that role's effective set in the same scope (groups → permissions, plus project-filtered direct permissions); **equality allowed** (Gate 1 question 2); an empty permission set and a request naming both `roleId` and `permissionIds` are `BadRequestError`; a non-covered set is `AuthorizationError('API key would exceed the creator's permissions')` naming the count, never the permission names. `assertCanManage({ scope, apiKeyId }, tx)` — the key's effective set (role or scopes) must be covered the same way by the caller. `attachableGrants(scope, tx)` — the cohort of S2.3. The handler calls `assertAttachable` in **both** the `AccountProject` and `OrganizationProject` create branches (a supplied or resolved role, or scopes) and `assertCanManage` before revoke, rotate and delete in **both** (today: organization only); `validateOrganizationProjectApiKeyRolePermission`, `validateCanManageOrganizationProjectApiKey` and the dead `filterApiKeysByManageable` are **removed** from the service and its port (`canAssignRole` stays for members and invitations). The tenant checks stay (`ensureOrganizationHasRole`, `ensureAccountHasRole`, the project exists). The handler accepts `permissionIds` internally (service and repository write the pivot rows) but **no transport exposes it yet**: `CreateApiKeyInput`, REST and OpenAPI are unchanged in this slice, so `boot-parity` and the GraphQL schema do not move.
- [ ] **S1.4 The hardened check is pinned by unit tests** (`api-key-attenuation.service.test.ts`, `api-keys.handler.attenuation.test.ts`), each a requirement: a creator may not bind a role whose effective set exceeds their own, whatever the role's level or lack of one; a creator whose own role has no level is bound by its own set; revoke, rotate and delete of a key whose effective set exceeds the caller's are refused, for both tenants; `AccountProject` with a supplied `roleId` whose effective set exceeds the caller's is refused, and the resolved default role passes; a key with no role and a permission set is manageable only by a caller whose set covers it; Owner → Owner-role key passes (equality); a machine-only permission is attachable by a holder of its gate and refused for a non-holder.

## Non-goals

- **Project-user API keys** (`projectUser`, `accountProjectUser`, `organizationProjectUser` scopes): they stay the credentials of their project user, with no role and no scopes; the dialog stays for them.
- **Changing the standard groups** or what any role holds, beyond adding `ApiKey:Update` to the three API-key groups; `canAssignRole` for members and invitations (`organization-members.service.ts`, `organization-invitations.service.ts`, the `members/*` web components) is unchanged.
- **Containment when authoring roles and groups** (`createRole`, `updateRole`, `addRoleGroup`, `assignRolePermission`, `assignGroupPermission`): a follow-up story with its own brief; this story's check compares a key's effective set with its creator's whatever the role contains.
- **Denying machine-only permissions to session principals** (Gate 1 question 5): the flag describes attachability; the session export used by the D21 e2e keeps working.
- **A union of role and scopes on one key** (Gate 1 question 1), **per-key permission conditions** beyond the rows' own conditions, **slug-named scopes** (`resource:action` strings, as project apps use) in the API, and **converting scopes back to a role**.
- **Migrating existing role keys automatically**: an owner may convert a key from its detail view (S2.4, S3.6); nothing is back-filled.

- **Account- and organization-scope keys** (`Tenant.Account` / `Tenant.Organization`), which the exchange does not support (`api-keys.service.ts:278-282`).
- **CDM import or export of project keys** (finding 9); receiver-side changes.

## Decisions for Gate 1

Each question has a recommended answer; the criteria above are written for it.

1. **Exclusive or union.** A project key carries **exactly one** of a role or a permission set (exclusive). **Recommended: exclusive.** One model per key, one effective set, one thing to show; a union would make the effective set "role ∪ scopes" and the picker a diff against a role. Alternative: union (scopes add to a role), which keeps old keys extensible without conversion but blurs what a key is.
2. **The attenuation comparand, and equality.** The creator's effective permission ids in the **key's project scope** (`OrganizationProject` / `AccountProject`), with the creator's actual token type, must contain the key's effective set (its permissions, or its role's groups and project-filtered direct permissions); **equality is allowed** (a key may do exactly what its creator can, like a personal access token). **Recommended as stated.** Consequence: an Owner may now create an Owner-role key, which today's `targetLevel > currentLevel` refuses; the member and invitation rule is unchanged. Alternative: strict subset for role keys to keep today's behaviour, at the cost of two rules for one check. Alternative comparand: the parent tenant scope (`Organization` / `Account`), as the request words it; it resolves through the same organization role for a session user but would not be transitive for a key creating a key, and the key never acts in that scope.
3. **Attenuation replaces `canAssignRole` for API keys entirely**: at create for both tenants, and for revoke, rotate and delete for both tenants (today organization only, account none). **Recommended: yes.** This is what findings 1 and 2 require, with one check. Alternative: keep the level check for standard roles beside containment (two paths).
4. **Machine-only rule and who may attach.** A standalone permission declares `attachableByHoldersOf: { resource, action }`; the export declares `ProjectUser:SetPassword`, which Owner, Admin and the account owners hold and Dev does not (`groups.ts:614-627`). **Recommended.** Alternative: `attachableBy: [OrganizationOwner, OrganizationAdmin, PersonalAccountOwner, OrganizationAccountOwner]`, which names roles inside a rule whose point is to stop depending on role names, and would need a role lookup the check otherwise does not make.
5. **Does "machine-only" also deny the permission to sessions?** **Recommended: no, not in this story.** The flag describes attachability; `exportProjectUserCredentials` with a session whose group holds the permission keeps working (the D21 e2e does exactly that). Alternative: enforce `TokenType.ApiKey` for machine-only permissions in `Grant.isAuthorized`, a behaviour change for existing grants, as a follow-up.
6. **Immutable or editable scopes.** **Recommended: editable** (S2.4, S3.6), overriding the first draft's lean to immutable, for these reasons: without an edit, every scope change forces a **new secret into every consumer** just to add a read, which pushes people to over-scope at creation, the opposite of what scopes are for; editing is exactly as sensitive as creation and uses **the same attenuation check** (additions must be covered by the editor's cohort; removals are always allowed), an audit row per change, an `api_key.updated` event and the existing per-principal cache invalidation; the key keeps its secret, so nothing new is handed out; the editor needs `ApiKey:Update` **and** the permissions being added; fine-grained tokens on the major platforms are editable. **Residual risk:** a key's reach can grow after its consumer was vetted. **Mitigation:** the `api_key.updated` event reaches security webhook subscribers, the audit rows name each added permission and who added it, and the detail view shows the current set; a consumer that wants a frozen key can be given no `ApiKey:Update` holder. Alternative: immutable (a change is a new key), which drops S2.4, S3.6's edit and conversion, one route and the event.
7. **One pivot table or two.** One `api_key_permissions` with `project_id` for RLS. **Recommended: one.** The permission set is a property of the key, the tenant is already on the existing pivot row, one repository and one resolution join serve both tenants; two tables would double the port, repository, service and the resolution path for no semantic gain. Alternative: `organization_project_api_key_permissions` and `account_project_api_key_permissions` mirroring the role columns.
8. **Permission ids or `resource:action` slugs in the API.** **Recommended: ids** (`permissionIds`). The resolution works on permission row ids (`getPermissionsByIds`), rows may carry conditions and custom permissions exist, the dashboard already works with `Permission` entities, and the cohort returns rows. Alternative: slugs, as project-app `scopes` are, which read better in a curl example but need a resolution step and cannot name a conditional row.
9. **Cohort query shape.** `apiKeyAttachableGrants(scope)` returning the attachable permissions (flagged `machineOnly`) **and** the attachable roles, gated by `ApiKey:Create`, no paging; a REST sibling. **Recommended.** Alternative: a filter on `permissions(scope)` plus the existing `roles(scope)` with client-side `canAssignRole`, which cannot express containment (finding 7).
10. **May an owner convert an existing role key to scopes?** **Recommended: yes, through `setApiKeyPermissions` from the detail view's explicit "Convert to scopes" action with its own confirmation (S3.6)**, one-way, bounded by the editor's cohort (not by the old role's set), audited with `fromRoleId`. No automatic migration, no toggle. Alternative: no conversion (a new key instead), which ties to question 6.
11. **Account-project keys get scopes too.** **Recommended: yes**, same model, same check, same cohort; the account owner's cohort is its own set plus the machine-only permissions it is gated for.
