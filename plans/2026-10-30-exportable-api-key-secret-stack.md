## Ordered slices (PRs)

Init `gh stack` with **slice 1 only**; `gh stack add` the next branch immediately before writing it.

**Order and the reason.** Slice 1 (the opt-in) is the smallest, carries the RBAC change and the one route, and is inert alone: nothing reads the flag yet, so it lands in the trunk whatever happens above it and is reviewable as "who may flip this and is it audited". Slice 2 (the copy, its form, the fingerprint) needs the flag to decide when to write and what form to issue, so it stacks on slice 1; it is inert for the receiver (a copy nobody can read, a fingerprint that says `exportable: true` with no way to export). Slice 3 (the export kind) needs the copy table and the unseal function from slice 2. The order is also Grant's layer order within each slice (database → schema → api). **Overlapping files found:** slices 1 and 2 both edit `apps/api/src/services/projects.service.ts` (slice 1 writes the flag and the audit row; slice 2 adds the copy deletion to the disable path), `docs/core-concepts/api-keys.md` (the same new section) and `rbac.md`; slices 2 and 3 both edit `apps/api/src/repositories/api-key-exportable-secrets.repository.ts` and its port (slice 3 adds the export read), `project-user-credential-exports.service.ts` is slice 3 only, `api-keys.service.ts` is slice 2 only. The stacking order resolves every overlap in one direction.

**Two-slice alternative (Gate 2 may pick it).** Merge slices 1 and 2 into `feat/exportable-api-key-secret-storage` (the request's suggested shape: storage + opt-in + fingerprint) above `-export`. One PR fewer and no shared-file overlap between 1 and 2, at the price of a single review covering RBAC, a new table, crypto and a format change together (about 650 source lines plus tests). Three is recommended because the opt-in review is a different question from the crypto review and a reviewer can hold one of them in their head at a time.

**Fan-out.** Slices are sequential by dependency (2 needs 1's flag; 3 needs 2's table): one writer at a time in this worktree. Within a slice: Verifier after the author; Security reads every slice as a reviewer who is not the author (agentic-sdlc § Fan-out), scheduled before that slice's gate 3, not folded into gate 4. Slice 3's ADR may be drafted while slice 2 is in review (a docs-only file, no conflict), by the slice 3 author.

**Size and the fallback seams.** Estimates: slice 1 about 180 lines of source (schema, migration, permission, service, handler, resolver, route, OpenAPI, REST schema, env declarations) and 350 of tests and docs; slice 2 about 420 and 700; slice 3 about 250 and 600 (plus the ADR). If an implemented diff is too large to review at once, the executor does **not** hand over a mega-diff: it stops and reports the split. Slice 1 has no seam worth cutting. Slice 2 splits at the seam the code has: `feat/exportable-api-key-secret-copy` (lib, table, migration, repository, port, the writes and deletions, service tests, sentinel) below `feat/exportable-api-key-secret-fingerprint` (`User.apiKeyCredentials`, its handler, resolver, repository read, e2e, docs); the copy slice alone is inert (nothing reads the table). Slice 3 has no seam (the kind, the read, the audit and the docs are one contract). These are fallbacks, not the plan.

**Could slice 1 be a plain PR to `main`?** Mechanically yes (it shares no file with `main`'s open work and `ci.yml` would run). Recommended to keep it in the stack: a flag that promises exportable secrets must not ship in a release where nothing is exportable, and the receiver pins one release with all three.

## Stack setup

Root the stack on the story trunk, never the default branch, or the slices target `main` and skip gate 4:

```sh
# Trunk — exists locally with the two plan files. After Gate 1: push it.
cd /Users/aleheredia/workspace/worktrees/grant-platform-feat-exportable-api-key-secret
sh .husky/pre-push && git -c core.hooksPath=.husky push -u origin feat/exportable-api-key-secret

# After Gate 2: init with the FIRST slice branch only.
gh stack init --base feat/exportable-api-key-secret feat/exportable-api-key-secret-opt-in

# After each slice: commit, then BOTH of these, every time.
gh stack submit --auto                                              # --auto: no interactive editor
gh stack link --base feat/exportable-api-key-secret <pr> <pr> …     # bottom to top; creates/grows the stack ON GitHub

# Before the NEXT slice — creates the branch on the current tip and pushes nothing:
gh stack add feat/exportable-api-key-secret-copy
# … work, commit, submit, link; then
gh stack add feat/exportable-api-key-secret-export

# After any merge, rebase or amend below a branch:
gh stack sync
```

Check positions before writing each slice, not after:

```sh
git for-each-ref --format='%(refname:short) %(objectname:short)' refs/heads
gh pr view <bottom-pr> --json baseRefName   # must be feat/exportable-api-key-secret, never main
```

`gh stack` cannot switch to a branch that is checked out in another worktree, so a slice written in a second worktree is pushed and its worktree removed before `gh stack` is asked to adopt or restack it. See [Agentic SDLC § GitHub stacking](../docs/contributing/agentic-sdlc.md#github-stacking). **`--base` is not optional on `link`.** `gh stack submit --auto` opens PRs as **drafts**; mark ready with `gh pr ready <pr>` for gate 3. Only the orchestrator runs `gh stack`; executors open plain PRs against the slice below.

**Hooks.** `git config core.hooksPath` is unset in this worktree (verified 2026-10-30), so: `git -c core.hooksPath=.husky commit` on every commit (lint-staged runs prettier); `sh .husky/pre-push` by hand before every push (`.husky/pre-push` is mode 755 at `42afcf0b`, so `git -c core.hooksPath=.husky push` runs it too; run it by hand regardless, it is the full chain: `format:check`, `lint`, the seven `dead-code:*` targets, `codegen:check`, `type-check`, `build`, `synth:check`, `CI=1 pnpm test`, `secret-scan:protect`); `pnpm release:check` by hand whenever a changeset is in the diff (a changeset naming an ignored package such as `@grantjs/core`, `@grantjs/database` or `@grantjs/constants` passes locally and fails CI). Never `--no-verify`, never `HUSKY=0`. Migrations: `pnpm --filter @grantjs/database db:generate`, rename the file (`0094_project_exportable_api_key_secrets.sql`, `0095_api_key_exportable_secrets.sql`), `db:migrate` against the local stack; the e2e stack picks them up through `scripts/e2e.sh`. **The sentinel strings in tests must not trip `secret-scan:protect`**: use the existing `sentinel-client-secret-never-leaves-…` pattern, never a string that looks like a real key. **`boot-parity`** changes by exactly one route on slice 1 and is unchanged on slices 2 and 3 (`apps/api/tests/e2e/__snapshots__/boot-parity.e2e.test.ts.snap`). The e2e environment needs `API_KEY_EXPORTABLE_SECRET_ENCRYPTION_KEY` wherever `PROJECT_OAUTH_CONNECTION_ENCRYPTION_KEY` is set for e2e (`docker-compose.e2e.yml`, `.env.test.example`), from slice 1 on. Agents never self-merge. Alejandro merges.
