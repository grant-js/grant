## Objective

A receiver that mirrors Grant into another system can create and delete users in both directions without duplicates or resurrections. Three upstream pieces: (1) a CDM import can say "this keyed user _is_ existing Grant user X", so a user created in Grant and copied to the other system is not created a second time when that system's export comes back; (2) the API-key lifecycle events name the key's owning user, so a revoke, rotate or create of a project user's key can be scoped to that user instead of a whole project; (3) a person who deletes their imported identity in Grant stays deleted: a tombstone the forward import respects.

## What is already true, and what is missing

Read from `origin/main` at `815495ea`.

### Part U3 — API-key events

**`api_key.deleted` already names the owner and the projects** (grant #558/#559): `ApiKeyService.deleteApiKey` reads the key's project links and its owning users before the delete (`apps/api/src/services/api-keys.service.ts:780-784`, `getOwningUserIds` at `apps/api/src/repositories/api-keys.repository.ts:268-276`) and publishes `subjectUserId` (the owner, only when there is exactly one in `project_user_api_keys`) and `projectIds` (`api-keys.service.ts:803-812`). The unit test pins it (`apps/api/tests/unit/services/api-keys.service.test.ts:255-310`), and the docs state the rule (`docs/core-concepts/events-webhooks-notifications.md:82`).

**`api_key.revoked` and `api_key.rotated` do not.** Both publish `aggregate` and `data` only (`api-keys.service.ts:673-680`, `:731-738`); no `subjectUserId`, no `projectIds`. **`api_key.created` does not either** (`:316-323`, `data.after` only). The requesting task is right on all three.

**Where these fields live, and what the receiver sees.** Neither field is in `data`. `subjectUserId` is a top-level field of the stored event and reaches the receiver as the `grantsubjectuser` envelope attribute (`apps/api/src/lib/webhooks/webhook-envelope.lib.ts:28`). `projectIds` is internal: it decides which projects' subscriptions receive the event and is "never part of the external envelope" (`packages/@grantjs/schema/src/events/event-envelope.ts:101-108`; fan-out in `apps/api/src/lib/webhooks/webhook-dispatcher.consumer.ts:22-25`). The request's wording "carry `subjectUserId` and `projectIds` in `data`" is therefore inexact; the criteria below say where each goes.

**`projectIds` is already derived for revoke and rotate.** The publisher adds the projects an aggregate is linked to at publish time (`apps/api/src/lib/events/drizzle-event-publisher.ts:63-84`, `:175`); `apiKey` is a project-linked kind (`apps/api/src/repositories/project-links.repository.ts:18-31`, `:103-125`, through the three API-key pivots). A revoke or rotate leaves the pivot in place, so the event already fans out to the owning project; only the explicit read a delete needs (links destroyed by the write) is missing, and here it is not needed. What revoke and rotate lack is **`subjectUserId` only**.

**`api_key.created` is published before the pivot exists, and that is why it names no project and no user.** The handler creates the key through the service (`apps/api/src/handlers/api-keys.handler.ts:131-138`), which publishes inside `createApiKey`, and only then writes the `project_user_api_keys` row (`:140-147`). At publish time the key is linked to nothing, so the derived `projectIds` is empty and the event reaches a project only through the request's scope (`webhookProjectIdsOf` also reads the scope's project, `webhook-dispatcher.consumer.ts:22-25`; a `projectUser` scope names one). The request's reading of the order is right.

**The order is not what a consumer sees, though.** Events are an outbox: the row is written in the request's transaction and relayed after commit (`events-webhooks-notifications.md` § Relay latency vs durability). A webhook or in-process consumer therefore never handles `api_key.created` before the pivot row is committed, whatever the order inside the transaction. The request's reason for moving the publish ("so a consumer reading the key's user on receipt finds it") is already satisfied; what is missing is the **content** of the event (`subjectUserId`, `projectIds`), which must be known at publish time. Finding 1 below.

**Notifications.** `api_key.created`, `.rotated` and `.revoked` notify the scope's `owners` only (`SECURITY_OWNERS`, `packages/@grantjs/schema/src/events/event-catalog.ts:62-66`, `:189-191`); the `subject` primitive is not in that rule (`apps/api/src/lib/notifications/audience-resolver.ts:146-148`), so a `subjectUserId` changes no recipient. It does let the rendered notification name the key's owner (`notification-display-context.ts:62`), inside Grant's own inbox.

### Part U2 — matching an imported user to an existing Grant user

**`findBy: id` already exists, and does something else.** The request says "today users are found by `email` or by `key` only". Not so: `CdmFindBy.Id` is accepted (`apps/api/src/lib/cdm/cdm-document.schemas.ts:30-34`; GraphQL `CdmKeyResolverInput.findBy`), documented (`docs/core-concepts/cdm-import-export.md:189`: "`key.value` is an existing Grant user id. Import skips global user provisioning and uses that user directly"), and used by the export for a member who has no provision key (`apps/api/src/lib/cdm/cdm-export-assemble.lib.ts:163`). In `expandCdmSyncInput` such a user produces **no `provisionedUsers` entry**, only a `userAssignments` entry with `userId` and no `userKey` (`apps/api/src/lib/cdm/expand-cdm-sync-input.lib.ts:128-144`, `:177-188`). So the row gets membership and roles, but **no `cdmImport` marker** on the membership row: `resolveAssignmentUserExternalKey` finds no key for a user the document did not provision (`apps/api/src/lib/cdm/entities/user-assignment.cdm-entity.ts:252-275`, `:580-592`, and the comment there says so). Later imports cannot key that user; a `findBy: key` document for the same person creates a second user. This is exactly the duplicate the request describes, and it is why `findBy: id` as it stands does not do the job.

**The key lookup reads the global user only.** `findUserIdByCdmImport` matches `users.metadata->'cdmImport'` for the project, kind and key (`apps/api/src/repositories/users.repository.ts:115-135`), never the membership row's marker that grant #568 writes (`apps/api/src/repositories/project-users.repository.ts:98-136`). A Grant-native user carries no global marker and, by policy, "the global metadata of a reused identity is never changed" (`cdm-import-export.md:398`). So writing the marker on the membership row, as the request asks, is **not enough for the second import to key the user**: the lookup has to read the row too. Finding 2.

**There is no tenant to check.** Grant users are global: `users` has no account or organization column and no RLS policy (`packages/@grantjs/database/src/schemas/users.schema.ts`); membership is `project_users`. `findBy: id` today attaches **any live user** to the importing project, and nothing else in the public API lets an operator attach an existing user by id (`addProjectUser` is called only from `createUser`, `apps/api/src/handlers/users.handler.ts:427`, and from project OAuth sign-in, `apps/api/src/handlers/project-oauth.handler.ts:1131`). The request's "refuses ids outside the tenant" has no referent in Grant's model; what the slice can refuse is a user that does not exist or is soft-deleted, and a marker conflict. Finding 3.

**Events: an import publishes nothing.** `importProjectCdm` runs under `runWithEventSuppression` (`apps/api/src/services/project-import.service.ts:267`), so "the same events as for a matched email identity today" is the empty list. The criterion stands, with that reading.

**Replace mode removes no membership.** Both user entities' `teardown` are no-ops (`user-provision.cdm-entity.ts:101-103`, `user-assignment.cdm-entity.ts:125-127`); users are global and memberships survive a replace. "The normal rule for imported users" on replace is therefore: nothing is removed.

**Export reads the global marker only.** `getProjectCdmProvisionedUsers` lists users whose **global** metadata names the project (`apps/api/src/repositories/project-export.repository.ts:797-815`), so a user matched by id and marked on the row only is exported as a `findBy: id` reference, not as a keyed `users[]` entry. Acceptable for this story (the receiver does not round-trip exports); listed as a non-goal.

**Cache invalidation after an import** collects the ids of `findBy: id` users for the auth-result cache (`apps/api/src/jobs/project-sync.job.ts:452-466`); a matched user gets new roles the same way and belongs in that list.

**Unused today:** `CdmKeyResolverInput.ifMissing` (`CdmIfMissing`) is accepted by the schema (`cdm-document.schemas.ts:33`) and read nowhere in `apps/api/src`. Not touched by this story; noted so nobody reaches for it.

### Part T — a deletion tombstone

**Nothing tombstone-like exists for identities.** The only "tombstone" in the repository is the CDM README's word for the soft-delete of CDM-managed rows on a replace import (`apps/api/src/lib/cdm/README.md:48`); naming the new table must not collide with that reading. `project-import.service.ts` skips nothing by design today; its one skip counter is `passwordsSkippedExisting` (credential ownership, `:353`).

**Self-deletion and operator deletion share one path.** `deleteOwnUser` resolves the caller and calls `deleteUser` (`apps/api/src/services/users.service.ts:323-335`); `deleteUser` (`:227-321`) already reads the membership rows and the global user's metadata to build `externalKeys` for `user.deleted` (`:272-283`; `resolveExternalKeys`, `apps/api/src/lib/events/event-external-keys.lib.ts:78-95`; `getUserMembershipMetadata`, `users.repository.ts:173-182`). The tombstone needs the same read, in the same transaction, at the same point; the actor is `this.user?.userId`.

**The marker key is an e-mail address for `findBy: email` identities** (`user-provision.cdm-entity.ts:68`, `:237-262`; row marker at `user-assignment.cdm-entity.ts:252-275`). A table keyed by `(projectId, kind, externalKey)` would therefore store the address of a person who just deleted themselves — the request forbids exactly that ("never the email"), and the request's assumption that the key is "the legacy user id" holds only for `findBy: key`. Finding 4.

**A soft-deleted identity's e-mail method stays live.** A soft delete sets `users.deleted_at` and removes credentials (`users.service.ts:305-318`); it does not touch `user_authentication_methods`. `findByEmail` queries the method table (`apps/api/src/repositories/user-authentication-methods.repository.ts:215-233`); whether its generic query also excludes rows whose user is soft-deleted is for the slice to confirm. If it does not, today's `applyEmailIdentity` re-attaches a soft-deleted user to the project on the next import (`user-provision.cdm-entity.ts:193-215`). The key path is safe (`findUserIdByCdmImport` filters `users.deleted_at`, `users.repository.ts:124`). Finding 5.

**Where a skip can be decided.** Each document user flows through three entities in order: provision (15), assignment (20), API keys (25) (`apps/api/src/lib/cdm/registry.ts:106-145`), sharing `ctx.produced.userIds` and `ctx.assignmentUserIds` (`packages/@grantjs/core/src/ports/services/cdm-entity-handler.port.ts:79-103`). A user the provision step does not resolve makes the assignment step throw `unresolved userKey` (`user-assignment.cdm-entity.ts:566-578`) and the API-key step look up nothing (`project-user-api-key.cdm-entity.ts:407`); the password step reads `produced.userIds` too (`user-provision.cdm-entity.ts:150-191`). So a skip recorded on the context by the provision step can silence all three without a second traversal.

**The receiver already learns of a self-deletion.** Since v1.20.2, `user.deleted` carries the user's import keys per project (`data.before.externalKeys`) and the envelope carries `grantactor` and `grantsubjectuser`, so a receiver can tell a self-deletion (actor is subject) from an operator deletion and from `project.user_removed`. The request's "readable by the reverse reconciler" criterion (2026-10-18) predates that. Finding 6.

**The retention job** hard-deletes the owner users of expired accounts (`apps/api/src/jobs/data-retention-cleanup.job.ts:47-55`), not soft-deleted users in general; a soft-deleted imported identity therefore stays in `users` indefinitely with its marker. Relevant to the lifetime question (Gate 1, question 6).

### Findings that shape the criteria

These came from reading the code, not from the request, and each changes a criterion.

1. **U3: the event's content, not its position, is the gap.** The outbox relays after commit, so moving the `api_key.created` publish after the pivot changes nothing a consumer can observe. What the event needs is the owner at publish time: the handler knows it (`projectId`, `userId` from the scope, `api-keys.handler.ts:130`) and can hand it to the service. Criterion U3.2 is written that way; the publish stays where it is.
2. **U2: the marker on the membership row is not enough.** The second import's `findBy: key` lookup reads the global user only; it must also read the live membership row of the importing project. Criterion U2.3.
3. **U2: "outside the tenant" has no referent.** Users are global; `findBy: id` already attaches any live user to the importing project and nothing in the public API does otherwise. The slice refuses a missing or soft-deleted user and a conflicting marker, and states plainly that membership comes from the document's assignment, as for `findBy: id`. Criterion U2.2 and Gate 1 question 3.
4. **T: the tombstone cannot store the key in clear.** For `findBy: email` identities the marker key is the address. The tombstone stores an HMAC-SHA256 fingerprint of the key (the CDM fingerprint secret already exists for API-key secrets, `apps/api/src/lib/cdm/cdm-api-key-fingerprint.lib.ts:46-48`, `CDM_API_KEY_FINGERPRINT_HMAC_SECRET`, `packages/@grantjs/env/src/schema.ts:227`, `apps/api/src/config/env.config.ts:1144`), and the import fingerprints the document's keys to match. Criterion T.1 and Gate 1 question 5. Consequence: "listed by external key" becomes "checked by external key" (finding 6).
5. **T: liveness on the e-mail path.** The skip rule is "a tombstone blocks the **creation** of an identity for the key"; for that to hold on the e-mail path, a method whose user is soft-deleted must not count as a live identity. Criterion T.3 and the precondition in the stack plan.
6. **T: the read API is not needed for the receiver to tell deletions apart**, and a key-in query must be a `POST` body (addresses never in URLs) with REST and GraphQL in sync (AGENTS.md), so it is its own slice and changes the `boot-parity` snapshot. Proposed deferred; Gate 1 question 8.

The read is extracted from `deleteApiKey` (`api-keys.service.ts:780-784`) into one private resolver the three methods share; no second rule. `projectIds` is passed explicitly for consistency with the delete (the publisher would derive the same set, finding "already derived"); the test asserts both. The envelope's `grantsubjectuser` names the user for a project-user key; `data.before` / `data.after` are unchanged.

### U2 — a keyed user document can name the existing Grant user it is (slice 2)

- [ ] **U2.1 The field.** `CdmKeyResolverInput.grantUserId: ID` (GraphQL, `packages/@grantjs/schema/src/schema/projects/inputs/sync-project-cdm.graphql`) and `cdmKeyResolverSchema.grantUserId: uuid, optional` (`cdm-document.schemas.ts:30-34`), carried as `CdmUserProvisionInternal.grantUserId` (`cdm-internal.types.ts:90-104`) by `expandCdmSyncInput`. Meaning: "when no user of this project carries this key yet, this existing Grant user is the one; mark them with the key". Valid only with `findBy: key` (the default): with `findBy: id` the value already is the id, with `findBy: email` the person is resolved by address; either combination is a `ValidationError` in `validateSyncInput` naming `users[index]`, never the key. (Gate 1 question 2 names the alternative shape.)
- [ ] **U2.2 The match rule, in `UserProvisionCdmEntity.apply` (key path, `user-provision.cdm-entity.ts:105-139`).** In order: (a) the project's key lookup (U2.3) finds a live user → if `grantUserId` is set and differs, refuse (`users[index]: grantUserId names another user than the one already imported under this key`); else reuse as today. (b) Nothing found and `grantUserId` set → the user must exist and be live (`users.deleted_at IS NULL`), else refuse (`users[index]: grantUserId does not name an existing user`); the user's live membership row for this project, if any, must not carry a marker with another key, and the user's global marker must not name this project with another key, else refuse (`users[index]: grantUserId is already imported under another key`); then record `produced.userIds[key] = grantUserId` and add to `assignmentUserIds`, **without** `createUser` and without touching the global user's metadata. The assignment step then writes the row marker as it does for every provisioned user (`user-assignment.cdm-entity.ts:252-275`), so the key sticks when the document assigns the user (roles, groups or permissions). A document that names the user and assigns nothing leaves them unmarked, with today's warning (`:231-235`); the next import with the hint matches again (idempotent). **Membership is not a precondition** (finding 3): as with `findBy: id` today, the document's assignment is what makes the user a member; the slice states this in the docs. Every refusal is a `ValidationError` that fails and rolls back the import like the other document rules, and names the position only (keys can be addresses; the by-reference path stores the message, `cdm-document.schemas.ts:286-297`). (Gate 1 question 3 names the stricter alternative.)
- [ ] **U2.3 The key lookup reads the membership row too.** `findUserIdByCdmImport` (`users.repository.ts:115-135`) also matches a live `project_users` row of the project whose `metadata->'cdmImport'` has the kind and key, joined to a live user (one query, `UNION` or `OR` over the join; the slice measures it stays on the existing GIN indexes, `users_metadata_idx`, `project_users_metadata_idx`). Global marker first, row second; the port's contract (`packages/@grantjs/core/src/ports/repositories/user.repository.port.ts`) says so. The e-mail path calls the same lookup (`user-provision.cdm-entity.ts:217-224`) and gains the same reach; harmless, stated in the PR body.
- [ ] **U2.4 Cache invalidation.** `collectUserIds` (`project-sync.job.ts:452-466`) includes `key.grantUserId` of each document user, so the matched user's auth-result cache is dropped like a `findBy: id` user's.
- [ ] **U2.5 Tests (QA).** Unit (`user-provision.cdm-entity.test.ts`): match recorded without `createUser`; existing key match with a different hint refused; missing user refused; soft-deleted user refused (the lookup used returns none for it); conflicting row marker refused; conflicting global marker refused; a hint with `findBy: email` and with `findBy: id` refused by `validateSyncInput` (`cdm-document.schemas.test.ts`); messages name the position, never the key or the id's owner. Repository test for U2.3 (global hit, row hit, soft-deleted user or soft-deleted row → none, another project's row → none). `expand-cdm-sync-input.lib.test.ts`: the hint is carried. E2E (Docker; the PR body says whether it ran): import 1 with `{ key: K, findBy: key, grantUserId: U }` and a role → `project_users(U, P).metadata.cdmImport` is `{ projectId: P, kind: 'user', externalKey: K }`, `users.metadata` of U unchanged, no new user row; import 2 of the same document **without** the hint → same user, no new row, `usersCreated: 0`; a document whose hint names a user id that does not exist → job fails with the position in the message; replace mode after import 1 → membership and marker unchanged (no removal, see "already true").
- [ ] **U2.6 Docs.** `docs/core-concepts/cdm-import-export.md:187-191` gets a fourth row (or a paragraph under the table) for `grantUserId`: what it does, the refusal rules, that membership comes from the assignment, and that the lookup reads the membership row; `:398` says the lookup reads the row. The GraphQL description of `CdmKeyResolverInput` says the same in two sentences. `apps/api/src/lib/cdm/README.md` names the new rule where it lists the user paths.
- [ ] **U2.7 Changeset.** `grant-api` and `@grantjs/schema` **minor** (same fixed group): "A CDM `users[]` entry keyed by `findBy: key` may name an existing Grant user with `key.grantUserId`; the import marks that user with the key for the importing project instead of creating a new one, and later imports resolve the key to the same user. The key lookup now also reads the project membership row's marker." `@grantjs/core` must not appear.

### T — a deletion tombstone the forward import respects (slice 3)

- [ ] **T.1 The table.** `cdm_import_tombstones` in `@grantjs/database` (`packages/@grantjs/database/src/schemas/cdm-import-tombstones.schema.ts`, exported from `schema.ts`): `id uuid pk`, `project_id uuid not null → projects(id) on delete cascade`, `kind varchar(50) not null` (`'user'` today), `external_key_fingerprint varchar(64) not null`, `created_at timestamp not null default now()`, unique `(project_id, kind, external_key_fingerprint)`, the same two RLS policies `project_users` has (`project-users.schema.ts:51-61`). Migration generated by `pnpm --filter @grantjs/database db:generate` and renamed `0093_cdm_import_tombstones.sql` (the repo renames generated files, e.g. `0092_admin_set_credential_source.sql`). **No key in clear, no user id, no copy of the record** (finding 4): the fingerprint is `HMAC-SHA256(secret, kind ⟂ externalKey)` with the CDM fingerprint secret, computed by a sibling of `fingerprintCdmApiKeySecret` in `cdm-api-key-fingerprint.lib.ts`. With an empty secret (`hmacSha256Hex` returns `''`, `apps/api/src/lib/token.lib.ts:80-85`) **no tombstone is written and a warning is logged** on the deletion; the docs say the secret is required for tombstones. (Gate 1 question 5.)
- [ ] **T.2 Written on self-deletion, same transaction.** In `UserService.deleteUser`, at the point that already reads the memberships and the global metadata (`users.service.ts:272-283`), when the actor is the subject (`this.user?.userId === id`, the `deleteOwnUser` path, `:323-335`): one row per project whose marker names the user — the live membership row's `cdmImport.externalKey` (kind `user`), else the global user's marker when it names that project — through a repository `insertIgnoringDuplicates`. The marker walk is shared with `resolveExternalKeys` by extracting its marker read (`event-external-keys.lib.ts:51-70`) into a function both call; the tombstone takes the **raw** marker key (an address included, it is hashed), never `cdmSource.legacy.id`. A Grant-native user (no marker anywhere) writes nothing. Hard and soft delete behave the same. An operator deleting someone else writes nothing (Gate 1 question 4). `removeProjectUser` is untouched and a test asserts it never calls the tombstone repository.
- [ ] **T.3 The import skips what a tombstone covers.** Rule: **a tombstone blocks the creation of an identity for its key in its project; it never blocks a document user that resolves to a live identity.** In `UserProvisionCdmEntity.apply`, at the two `createUser` sites (`user-provision.cdm-entity.ts:133`, `:244`) and nowhere else: when the key's fingerprint is tombstoned for `ctx.projectId` (one repository read per import, fingerprints computed once before the loop), the row is **skipped**: not created, not recorded in `produced.userIds`, its key added to a new `ctx.skippedUserKeys: Set<string>` (`CdmApplyContext`, core port), `ctx.result.usersSkippedTombstoned += 1`. Downstream: the assignment step drops an entry whose `userKey` is skipped instead of throwing (`user-assignment.cdm-entity.ts:566-578`; membership, roles, groups, permissions, tags: none written), the API-key step drops its keys (`project-user-api-key.cdm-entity.ts:407`), `postApply` drops its password (the project credential, ADR 0011). ## Decisions for Gate 1

Each question has a recommended answer; the criteria above are written for it.

1. **U3: content, not order.** Keep the `api_key.created` publish where it is and pass the owner into the service (`createApiKey(params.owner)`), because the outbox relays after commit and the order inside the transaction is unobservable (finding 1); the docs say so. **Recommended: yes.** Alternative: a `publishCreated` service method the handler calls after the pivot (same content, two steps, the handler orchestrates an event).
2. **U2: shape of the hint.** `key.grantUserId` on a `findBy: key` user ("this key _is_ this user"), so the document keeps the same key on every import and the hint is optional and idempotent. **Recommended.** Alternative: `findBy: id` plus a new `users[].externalKey` to mark with — the document must switch resolvers between the first and later imports, and `findBy: id` keeps its present meaning for everyone else only if the field is absent.
3. **U2: what a match requires.** (A) The user exists and is live, no conflicting marker; membership comes from the document's assignment, as for `findBy: id` today (finding 3). **Recommended**: an operator who removed the user from the project and re-imports gets them back with the right key, which is the behaviour the D12 addendum already expects of admin removals. (B) Stricter: the user must already be a live member of the project; a re-import after a removal is refused, and dropping the hint to get past it creates the duplicate this slice exists to prevent.
4. **T: which deletions write a tombstone.** Self-deletion only (actor is subject), as the request says. **Recommended**: an operator's deletion of someone else stays recoverable by the next import, and this story has no way to lift a tombstone. Alternative: every `deleteUser` of a marked identity (one `if` less; needs the removal mutation in the same story).
5. **T: what the tombstone stores.** `(project_id, kind, HMAC-SHA256 fingerprint of the key)` with the existing CDM fingerprint secret; nothing in clear (finding 4). **Recommended.** With an empty secret: write nothing and warn (recommended), or fall back to a plain SHA-256 (weaker for addresses; two code paths). Alternative to the whole approach: store the key in clear and accept that e-mail-keyed identities leave their address in the table — contradicts the request's own rule.
6. **T: lifetime and removal.** Forever; Grant never removes a tombstone; a person who recreates an identity in Grant is not blocked (the rule blocks creation only, criterion T.3), so removal is rarely needed; an operator lifts one by a database operation until a later story adds a mutation; the docs say exactly this. **Recommended.** Alternative: a `removeCdmImportTombstone` mutation in this story (a fourth slice, REST + GraphQL, snapshot change).
7. **T: the skip rule.** "Blocks the creation of an identity for the key; never blocks a document user that resolves to a live identity." **Recommended** (it also answers "the person is invited again"). Alternative: block the key outright until the tombstone is lifted (simpler read, needs question 6's mutation to be usable).
8. **T: the read API for the receiver.** Defer to a follow-up: since v1.20.2 `user.deleted` carries the key and the actor, which is what the receiver needed the listing for (finding 6); a listing by key is impossible with fingerprints (question 5) and a keys-in check must be a `POST` body with REST and GraphQL in sync, its own slice. **Recommended: defer.** Alternative: slice 4, `POST /api/projects/{id}/sync/tombstones/check` + `cdmImportTombstoned` query, security-full, `boot-parity` changes by one route.
9. **Review bars.** Slice 1 (U3) **light**: ids only, no key material, the owner rule already ships, audience unchanged; Security comments. Slice 2 (U2) **security-full**: binding a user to a key and a project by id, new tenancy-shaped lookup. Slice 3 (T) **security-full**: deletion path, fingerprint of a possible address, new RLS table, import drops rows. **Recommended as stated.**
10. **Release.** Minor, **v1.21.0** (a migration, a new import field, a new result field; the patch precedent, v1.20.2, was one additive envelope field without a migration). **Recommended: minor.** Alternative: patch v1.20.3.
